设备驱动模型（Device Driver Model）

非官方简体中文译本 · H01 · 英文基线 4.5.99 · 全站目录（79 篇） · H 批目录 · 本页英文原文

简介

Zephyr 内核支持多种设备驱动。某个驱动能否使用取决于板卡和驱动本身。

Zephyr 设备模型为系统中各驱动提供统一的配置方式，并负责初始化所有已配置纳入系统的驱动。

每类驱动（如 UART、SPI、I2C）均有相应的通用 API。

在这种模型下，驱动在初始化时设置指针，指向含有各 API 函数指针的结构。相关结构按初始化级别的顺序放在 RAM 段中。

官方原图：设备驱动模型：设备对象如何关联配置数据、运行时数据和 API 函数表

标准驱动

下列设备驱动存在于所有受支持的板级配置上。

  • 中断控制器：供内核的中断管理子系统使用。

  • 定时器：供内核的系统时钟和硬件时钟子系统使用。

  • 串行通信：供内核的系统控制台子系统使用。

  • 熵源（entropy）：为随机数生成子系统提供熵源。

    重要

    获取随机值应使用随机数 API。不要把熵源函数直接当作随机数生成器：部分硬件仅提供用于播种的熵，不能产生满足密码学安全要求的随机数流。

同步调用

Zephyr 为多种开发板提供设备驱动。除非硬件根本不提供中断，否则驱动应支持基于中断的实现，而不应依赖轮询。

通过 i2c.h 或 spi.h 等设备专用 API 发出的高层调用通常是同步的，因此这些调用应该阻塞至完成。

驱动 API

下列 API 由 device.h 提供，只供设备驱动内部使用，应用程序不应使用。

DEVICE_DEFINE()

创建设备对象及相关数据结构，并登记启动时的初始化操作。

DEVICE_NAME_GET()

将设备标识符转换为设备对象的全局标识符。

DEVICE_GET()

按名称获取设备对象指针。

DEVICE_DECLARE()

声明设备对象。需要前向引用尚未定义的设备时使用。

DEVICE_API()

包装驱动 API 声明，将其放入对应的链接段。实现上游驱动类别必须使用此宏：DEVICE_API_GET 和 DEVICE_API_IS 依赖每类 API 的实例位于对应链接段，才能在运行时验证设备的 API 类别。

驱动数据结构

设备初始化宏在构建时填充数据结构，分为只读部分和运行时可变部分。概括如下：

struct device {
      const char *name;
      const void *config;
      const void *api;
      void * const data;
};

config 成员指向构建时确定的只读配置，如内存映射 I/O 基址、IRQ 线号及设备的其他固定硬件特性。它对应传给 DEVICE_DEFINE() 及相关宏的 config 指针。

data 结构位于 RAM，驱动在运行时用它保存每个实例的状态，如引用计数、信号量、临时缓冲区等。

api 结构将通用子系统 API 映射到本驱动的设备专用实现。它通常是只读的，在构建时填充，详见下一节。

子系统与 API 结构

大多数驱动实现与具体设备无关的子系统 API。应用面向这一通用 API 编程，无须依赖某个驱动实现。

必须用 DEVICE_API() 声明驱动 API 实例，才能将其实例放入对应的 API 链接段。这样 DEVICE_API_GET、DEVICE_API_IS 才能在运行时验证设备的 API 是否属于预期类别。

子系统 API 的定义通常如下：

typedef int (*subsystem_do_this_t)(const struct device *dev, int foo, int bar);
typedef void (*subsystem_do_that_t)(const struct device *dev, void *baz);

__subsystem struct subsystem_driver_api {
      subsystem_do_this_t do_this;
      subsystem_do_that_t do_that;
};

static inline int subsystem_do_this(const struct device *dev, int foo, int bar)
{
      return DEVICE_API_GET(subsystem, dev)->do_this(dev, foo, bar);
}

static inline void subsystem_do_that(const struct device *dev, void *baz)
{
      DEVICE_API_GET(subsystem, dev)->do_that(dev, baz);
}

驱动实现该子系统的各个函数，再用 DEVICE_API() 包装并填充一个 subsystem_driver_api 结构实例：

static int my_driver_do_this(const struct device *dev, int foo, int bar)
{
      ...
}

static void my_driver_do_that(const struct device *dev, void *baz)
{
      ...
}

static DEVICE_API(subsystem, my_driver_api_funcs) = {
      .do_this = my_driver_do_this,
      .do_that = my_driver_do_that,
};

随后把 my_driver_api_funcs 作为 DEVICE_DEFINE() 的 api 参数传入。

说明

api 结构引用了各 API 函数，即使应用未调用它们，函数也会进入二进制；链接器的 gc-sections 选项总能看到至少一个引用。因此，要使链接阶段能裁掉可选驱动功能，通常须用 Kconfig 选项控制该功能。

API 类继承

子系统 API 可扩展另一个子系统 API，形成父子关系。实现子 API 的设备也被识别为实现了父 API。例如 I3C 控制器扩展了 I2C API，可用于要求 I2C 设备的场合。

定义子 API 时，将父 API 结构嵌入为子结构的第一个成员，并通过 DEVICE_API_EXTENDS 声明继承关系：

__subsystem struct child_driver_api {
      struct subsystem_driver_api parent_api;
      child_do_extra_t do_extra;
};

DEVICE_API_EXTENDS(child, subsystem, parent_api);

实现子 API 的驱动需同时填充父、子两级的方法：

static DEVICE_API(child, my_child_api) = {
      .parent_api = {
              .do_this = my_child_do_this,
              .do_that = my_child_do_that,
      },
      .do_extra = my_child_do_extra,
};

这样，DEVICE_API_IS 对父类和子类都会返回真，DEVICE_API_GET 也能以任一类型取得 API：

/* Both return true for a child device */
DEVICE_API_IS(subsystem, dev);
DEVICE_API_IS(child, dev);

/* Access through parent API */
DEVICE_API_GET(subsystem, dev)->do_this(dev, foo, bar);

支持多级继承，例如孙类扩展子类、子类扩展父类。同一父类下的不同子类也能由 DEVICE_API_IS 正确区分。

设备专用 API 扩展

有些设备既能作为 GPIO 等子系统的实例，又提供标准 API 无法表达的功能。这类设备除子系统操作外，还在设备专用头文件中提供扩展 API。

设备专用 API 的定义通常如下：

#include <zephyr/drivers/subsystem.h>

/* When extensions need not be invoked from user mode threads */
int specific_do_that(const struct device *dev, int foo);

/* When extensions must be invokable from user mode threads */
__syscall int specific_from_user(const struct device *dev, int bar);

/* Only needed when extensions include syscalls */
#include <zephyr/syscalls/specific.h>

扩展子系统功能的驱动会同时实现子系统 API 和专用 API：

static int generic_do_this(const struct device *dev, void *arg)
{
   ...
}

static struct generic_api api {
   ...
   .do_this = generic_do_this,
   ...
};

/* supervisor-only API is globally visible */
int specific_do_that(const struct device *dev, int foo)
{
   ...
}

/* syscall API passes through a translation */
int z_impl_specific_from_user(const struct device *dev, int bar)
{
   ...
}

#ifdef CONFIG_USERSPACE

#include <zephyr/internal/syscall_handler.h>

int z_vrfy_specific_from_user(const struct device *dev, int bar)
{
    K_OOPS(K_SYSCALL_SPECIFIC_DRIVER(dev, K_OBJ_DRIVER_GENERIC, &api));
    return z_impl_specific_do_that(dev, bar)
}

#include <zephyr/syscalls/specific_from_user_mrsh.c>

#endif /* CONFIG_USERSPACE */

应用可以通过这两种 API 使用设备。

一个驱动、多个实例

系统可有同一驱动的多个实例，例如多个 GPIO 端口组或多个 UART。每个实例有独立的 config 结构和 data 结构。

多实例的中断配置需要特殊处理。由于 IRQ_CONNECT() 的参数必须能在构建时解析，若各实例使用不同的中断线，可为每个实例提供单独的配置函数。

例如，要为 my_driver 配置两个使用不同中断线的实例。在 drivers/subsystem/subsystem_my_driver.h 中：

typedef void (*my_driver_config_irq_t)(const struct device *dev);

struct my_driver_config {
      DEVICE_MMIO_ROM;
      my_driver_config_irq_t config_func;
};

在通用初始化函数的实现中：

void my_driver_isr(const struct device *dev)
{
      /* Handle interrupt */
      ...
}

int my_driver_init(const struct device *dev)
{
      const struct my_driver_config *config = dev->config;

      DEVICE_MMIO_MAP(dev, K_MEM_CACHE_NONE);

      /* Do other initialization stuff */
      ...

      config->config_func(dev);

      return 0;
}

声明具体实例时：

#if CONFIG_MY_DRIVER_0

DEVICE_DECLARE(my_driver_0);

static void my_driver_config_irq_0(const struct device *dev)
{
      IRQ_CONNECT(MY_DRIVER_0_IRQ, MY_DRIVER_0_PRI, my_driver_isr,
                  DEVICE_GET(my_driver_0), MY_DRIVER_0_FLAGS);
}

const static struct my_driver_config my_driver_config_0 = {
      DEVICE_MMIO_ROM_INIT(DT_DRV_INST(0)),
      .config_func = my_driver_config_irq_0
}

static struct my_data_0;

DEVICE_DEFINE(my_driver_0, MY_DRIVER_0_NAME, my_driver_init,
              NULL, &my_data_0, &my_driver_config_0,
              POST_KERNEL, MY_DRIVER_0_PRIORITY, &my_api_funcs);

#endif /* CONFIG_MY_DRIVER_0 */

注意这里用 DEVICE_DECLARE() 解除循环依赖：中断处理程序需要设备作为参数，而设备本身此时还在定义中。

初始化级别

一个驱动可能依赖其他驱动先初始化，或者需要使用内核服务。通过 DEVICE_DEFINE() 和相关 API 可以指定启动时调用初始化函数的时机。设备驱动从下面三个初始化级别中选一个：

PRE_KERNEL_1

适用于无依赖的设备，如只依赖处理器／SoC 自带硬件的设备。此时内核服务尚不可用，配置时不能调用；中断子系统已就绪，可以设置中断。初始化函数在中断栈上运行。

PRE_KERNEL_2

适用于依赖 PRE_KERNEL_1 阶段已初始化设备的驱动。此时内核服务仍不可用，初始化函数也在中断栈上运行。

POST_KERNEL

适用于配置时需要内核服务的设备。初始化函数在内核主任务的上下文中运行。

同一级别内可用优先级指定各设备的相对顺序。取值 0–999，数值越小，初始化越早。须使用无符号、无前导零的十进制整数字面值（如 32）或等价的符号名（如 \#define MY_INIT_PRIO 32）；不允许使用表达式（如 CONFIG_KERNEL_INIT_PRIORITY_DEFAULT + 5）。

驱动及系统工具可用 k_is_pre_kernel() 判断当前是否仍处于内核启动前阶段。

延迟初始化

也可延迟初始化。此时 Zephyr 不在启动时自动初始化设备，而在应用调用 device_init() 时才初始化。要启用，请在 DTS 中的相应节点加入 zephyr,deferred-init 属性。例如：

/ {
        a-driver@40000000 {
                reg = <0x40000000 0x1000>;
                zephyr,deferred-init;
        };
};

说明

有些驱动依赖启动时即已初始化，延后操作可能无法正常工作。网络驱动目前不支持延迟初始化。

系统驱动

如果只想在启动时运行一个函数，可以使用 SYS_INIT。它不接受配置或运行时数据结构，之后也不能按名称获得设备指针；初始化级别和优先级规则与设备相同。

查看初始化顺序

通过 DEVICE_DEFINE（或其变体）及 SYS_INIT 声明的驱动或初始化项，会在启动时按指定级别、优先级依次调用初始化函数。

要检查链接器最终生成的初始化调用顺序，可使用 initlevels CMake 目标，例如 west build -t initlevels。

错误处理

除非故障属于正常运行中预期会发生的情况（如存储设备已满），一般应使用 __ASSERT()，而不是层层返回错误值。无效参数、编程错误、一致性检查失败和不可恢复的异常等，适合用断言处理。

如果错误应交由调用者处理，则成功返回 0，失败返回 POSIX errno.h 错误码。详见错误码。

内存映射

某些系统不能在构建时确定外设内存映射 I/O（MMIO）区域的线性地址：

  • 例如 PCI Express 总线需要在运行时探测 I/O 范围。

  • 如果启用了内存管理单元（MMU），需要将 MMIO 的物理地址映射到页表中某个由内核确定的虚拟地址。

此类系统须在 RAM 中保存 MMIO 区域信息，并在驱动初始化时建立映射。其他系统可直接采用 DTS 中的物理地址，无须在 RAM 中另存。

为此类驱动提供了 DEVICE_MMIO 系列 API 和映射函数 device_map()。

只有一个 MMIO 区域的设备模型驱动

最简单的是只管理一个 MMIO 区域。驱动分别在 config_info 和 driver_data 中使用 DEVICE_MMIO_ROM、DEVICE_MMIO_RAM，用 DEVICE_MMIO_ROM_INIT 从 DTS 初始化 config_info，并在初始化函数中调用 DEVICE_MMIO_MAP()：

struct my_driver_config {
   DEVICE_MMIO_ROM; /* Must be first */
   ...
}

struct my_driver_dev_data {
   DEVICE_MMIO_RAM; /* Must be first */
   ...
}

const static struct my_driver_config my_driver_config_0 = {
   DEVICE_MMIO_ROM_INIT(DT_DRV_INST(...)),
   ...
}

int my_driver_init(const struct device *dev)
{
   ...
   DEVICE_MMIO_MAP(dev, K_MEM_CACHE_NONE);
   ...
}

int my_driver_some_function(const struct device *dev)
{
   ...
   /* Write some data to the MMIO region */
   sys_write32(0xDEADBEEF, DEVICE_MMIO_GET(dev));
   ...
}

宏的展开随配置而异。在没有 MMU 和 PCIe 的设备上，DEVICE_MMIO_MAP 和 DEVICE_MMIO_RAM 均展开为空。

具有多个 MMIO 区域的设备模型驱动

有些驱动有多个 MMIO 区域，也可能因使用了继承而要求将其他数据放在 config_info、driver_data 的首位。

此时可用 DEVICE_MMIO_NAMED 系列宏。须定义 DEV_CFG()、DEV_DATA()，以获得类型正确的 config_info 或 dev_data 指针。例如：

struct my_driver_config {
   ...
     DEVICE_MMIO_NAMED_ROM(corge);
     DEVICE_MMIO_NAMED_ROM(grault);
   ...
}

struct my_driver_dev_data {
        ...
     DEVICE_MMIO_NAMED_RAM(corge);
     DEVICE_MMIO_NAMED_RAM(grault);
     ...
}

#define DEV_CFG(_dev) \
   ((const struct my_driver_config *)((_dev)->config))

#define DEV_DATA(_dev) \
   ((struct my_driver_dev_data *)((_dev)->data))

const static struct my_driver_config my_driver_config_0 = {
   ...
   DEVICE_MMIO_NAMED_ROM_INIT(corge, DT_DRV_INST(...)),
   DEVICE_MMIO_NAMED_ROM_INIT(grault, DT_DRV_INST(...)),
   ...
}

int my_driver_init(const struct device *dev)
{
   ...
   DEVICE_MMIO_NAMED_MAP(dev, corge, K_MEM_CACHE_NONE);
   DEVICE_MMIO_NAMED_MAP(dev, grault, K_MEM_CACHE_NONE);
   ...
}

int my_driver_some_function(const struct device *dev)
{
   ...
   /* Write some data to the MMIO regions */
   sys_write32(0xDEADBEEF, DEVICE_MMIO_GET(dev, grault));
   sys_write32(0xF0CCAC1A, DEVICE_MMIO_GET(dev, corge));
   ...
}

同一设备树节点内有多个 MMIO 区域的驱动

同一设备树节点也可以用 reg-names 属性区分多个 MMIO 区域。例如：

/dts-v1/;

/ {
        a-driver@40000000 {
                reg = <0x40000000 0x1000>,
                      <0x40001000 0x1000>;
                reg-names = "corge", "grault";
        };
};

处理方式与上一节类似，但改用 DEVICE_MMIO_NAMED_ROM_INIT_BY_NAME。因此只有驱动配置结构不同：

const static struct my_driver_config my_driver_config_0 = {
   ...
   DEVICE_MMIO_NAMED_ROM_INIT_BY_NAME(corge, DT_DRV_INST(...)),
   DEVICE_MMIO_NAMED_ROM_INIT_BY_NAME(grault, DT_DRV_INST(...)),
   ...
}

不使用 Zephyr 设备模型的驱动

某些驱动或类似驱动的代码不使用 Zephyr 设备模型，例如定时器驱动或中断控制器代码；必须另行安排 MMIO 信息的存储。

可使用 DEVICE_MMIO_TOPLEVEL 系列宏，例如：

DEVICE_MMIO_TOPLEVEL_STATIC(my_regs, DT_DRV_INST(..));

void some_init_code(...)
{
   ...
   DEVICE_MMIO_TOPLEVEL_MAP(my_regs, K_MEM_CACHE_NONE);
   ...
}

void some_function(...)
   ...
   sys_write32(DEVICE_MMIO_TOPLEVEL_GET(my_regs), 0xDEADBEEF);
   ...
}

不使用 DTS 的驱动

有些驱动不从 DTS 获取 MMIO 物理地址，例如 PCIe。此时可直接调用 device_map()：

void some_init_code(...)
{
   ...
   struct pcie_bar mbar;
   bool bar_found = pcie_get_mbar(bdf, index, &mbar);

   device_map(DEVICE_MMIO_RAM_PTR(dev), mbar.phys_addr, mbar.size, K_MEM_CACHE_NONE);
   ...
}

这些情况下可省略 DEVICE_MMIO_ROM 声明。
