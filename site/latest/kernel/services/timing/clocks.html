内核计时（Kernel Timing）

非官方简体中文译本 · E04 · 英文基线 4.5.99 · 全站目录（94 篇） · E 批目录 · 本页英文原文

Zephyr 提供可扩展的计时框架，可从任意精度的硬件时钟源报告和跟踪定时事件。

时间单位

内核使用几种时间单位，各有用途。

应用代码默认用毫秒或微秒等实际时间单位表示时间。这样的表示易于理解，也便于跨平台使用，但不一定完全符合底层硬件的精度。

内核通过 k_cycle_get_32() 和 k_cycle_get_64() 提供周期（cycle）计数。它旨在提供操作系统可向用户开放的最快计数器（例如 CPU 周期计数器），读取操作也应很快。对时间极其敏感的代码可以轮询它以获得尽可能高的精度。可用 sys_clock_hw_cycles_per_sec() 查询其频率。在多数平台上，该频率等于 CONFIG_SYS_CLOCK_HW_CYCLES_PER_SEC，系统运行期间保持不变。如果平台的系统定时器频率可变，sys_clock_hw_cycles_per_sec() 返回运行时的实际值，应用不得假设它恒定。

运行时系统定时器频率

有些平台须在运行时确定系统定时器频率，因为驱动要从硬件获知频率，或者启动后频率仍可能改变。

能在运行时改变系统定时器工作频率的平台必须启用 CONFIG_SYSTEM_CLOCK_HW_CYCLES_PER_SEC_RUNTIME_UPDATE，并执行以下操作：

  • 更改时钟后，调用 z_sys_clock_hw_cycles_per_sec_update()。

  • 若驱动缓存了派生常量（如每个节拍包含的周期数），或在时钟变化后需重新设置硬件，应由定时器驱动覆盖实现 z_sys_clock_hw_cycles_per_sec_update()。

z_sys_clock_hw_cycles_per_sec_update() 的默认实现仅更新已存储的频率值。

说明

CONFIG_SYSTEM_CLOCK_HW_CYCLES_PER_SEC_RUNTIME_UPDATE 使用单一全局值跟踪系统定时器频率。它不适用于不同 CPU 可能观察到不同系统定时器频率的逐 CPU 调频配置。

启用后，sys_clock_hw_cycles_per_sec() 的返回值及时间单位换算均使用当前运行时频率。

对异步计时，内核以节拍（tick）为单位记录运行时间和超时。中断应尽可能在节拍边界到来，不跟踪小数节拍。节拍率由 CONFIG_SYS_CLOCK_TICKS_PER_SEC 配置。大多数能任意设置中断超时的硬件平台，默认值预计在 10 kHz 量级；软件仿真平台和旧式驱动通常使用传统的 100 Hz。

时间单位换算

Zephyr 的换算库支持毫秒（ms）、微秒（us）、节拍（tick）与周期（cyc）之间的任意换算。每种换算均可指定取整方向：floor 向下、ceil 向上、near 取最近值；输出精度可选 32 位或 64 位。

例如，k_ms_to_ticks_ceil32() 把毫秒数换算为节拍数并向上取整，结果截为 32 位；k_cyc_to_us_floor64() 把测得的周期数换算为已过的微秒数，向下取整并保留完整的 64 位精度。全部换算函数见参考文档。

在各计数频率互为整数倍且结果能存入一个机器字的大多数平台上，这些换算可展开为 2 至 4 个操作；只有确实需要并请求完整精度时才支付相应开销。

系统运行时间（uptime）

内核替应用跟踪系统自启动以来的运行时间。可随时调用 k_uptime_get() 读取以毫秒计的值。大多数跨平台应用可使用这一接口。

内部则以 64 位整数记录经过的节拍数。计时要求精确、愿意自行换算实际时间单位的应用可通过 k_uptime_ticks() 读取它。

k_uptime_delta() 可计算参考时刻与当前时刻之间的时间差，并将参考时刻更新为当前运行时间，方便计算下一次间隔。

超时（timeouts）

Zephyr 许多内核 API 都带有超时参数，用来表示事件将在何时发生。例如：

  • k_sem_take()、k_queue_get() 等阻塞操作可以指定超时；到时仍没有可用资源或数据，函数便返回错误码。

  • 内核 k_timer 对象必须指定首次到期时长和后续周期。

  • 内核 k_work_delayable API 的超时参数指定何时将工作项加入系统工作队列。

这些时间都用 k_timeout_t 表示。它是不透明的结构类型，必须用内核提供的一组超时宏之一初始化。最常用的是 K_MSEC，表示相对于当前时刻的毫秒数。

相对超时所说的“当前时刻”取决于调用上下文：

  • 在超时回调内安排新的相对超时（例如传给 k_timer_init() 的到期函数或传给 k_work_init_delayable() 的工作处理函数）时，“当前时刻”是本次超时原定触发的精确时刻，即使实际时间已经向前推进。这样，回调中安排的定时器相对于上次预定到期时刻具有精确偏移，可定期触发而不积累系统性时钟漂移。

  • 在应用上下文中安排超时时，“当前时刻”是内核收到该超时值时 k_uptime_ticks() 返回的值。

其他初始化宏沿用前述单位约定。K_NSEC()、K_USEC、K_TICKS、K_CYC() 分别以纳秒、微秒、节拍、周期指定距到期的时间。

k_timeout_t 的精度可配置，默认为 32 位。用非节拍单位表示很长的运行时间时，回绕行为比较复杂；因此，长时间运行且对计时敏感的应用宜使用 64 位超时类型。

也可以用自系统启动以来的绝对时间指定超时。以 K_TIMEOUT_ABS_MS 初始化时，系统运行时间达到指定值后超时；另有纳秒、微秒、周期、节拍版本。

内核计时的内部机制

超时队列

以上 API 指定的所有 k_timeout_t 事件都由一个全局队列管理。请求事件的子系统提供回调函数指针，指定到期后的动作，并提供 _timeout 跟踪结构。该结构应嵌入子系统自己的数据结构，例如 wait_q 或 k_tid_t 线程结构。

通过 k_timeout_t 传入的各种单位只在入队时换算为节拍一次，内核内部不反复转换。因此，无论事件多少、超时多长，均保持节拍级精度。

通过 CONFIG_TIMEOUT_BACKEND 在构建时选择队列数据结构。不同后端仅共享前端：节拍通告路径、SMP 重入处理及相对与绝对超时规则。队列本身由各后端实现，因此可按负载选型，无须更改公共代码。

默认后端 CONFIG_TIMEOUT_BACKEND_DLIST 采用按到期顺序排列的双向链表，每项存储相对前一项的节拍差。若有 N 个待处理超时，插入为 O(N)。通常只有少数超时时代价很低，但大量超时并存时扩展性较差。另有四种实验性实现，以更多内存或不同的行为换取大规模插入性能：

  • CONFIG_TIMEOUT_BACKEND_MINHEAP 用绝对到期时间作键，将事件存入二叉最小堆，插入和移除均为 O(log N)。要求 64 位节拍（CONFIG_TIMEOUT_64BIT）和固定容量的堆（CONFIG_TIMEOUT_HEAP_MAX_ENTRIES，溢出为致命错误），不保证同一节拍到期的事件按原顺序触发。

  • CONFIG_TIMEOUT_BACKEND_WHEEL 是分层时间轮：近期事件的插入和移除为 O(1)，超出范围的事件进入有序溢出链表。它的每事件开销和静态占用最大，不保持同节拍触发顺序。由于下一次超时的估算受轮周期限制，无节拍空闲的 CPU 也会被周期性唤醒，产生其他后端没有的功耗。

  • CONFIG_TIMEOUT_BACKEND_BUCKET 是单层分桶差分链表，可视为简化的时间轮。在可调的近期窗口（CONFIG_TIMEOUT_BUCKET_LISTS）内插入为 O(1)，超出窗口则进入有序溢出链表。它也要求 64 位节拍，但与时间轮不同，它保持同节拍触发顺序，不额外唤醒空闲 CPU。

  • CONFIG_TIMEOUT_BACKEND_SKIPLIST 是以绝对到期时间为键的 Pugh 跳表。插入和移除的期望复杂度为 O(log N)，没有固定容量上限；同节拍到期按先进先出顺序触发。它需要 64 位节拍。每个事件存储 CONFIG_TIMEOUT_SKIPLIST_MAX_LEVEL 个前向指针，因此每事件 RAM 占用高于差分链表或最小堆。

非默认后端适用于同时维护大量超时的系统，尤其是超时集中在近期的系统。多数应用继续使用默认差分链表即可。

定时器驱动

内核的节拍级计时由定时器驱动提供。接口和锁定规则见系统定时器驱动。

时间片轮转

计时子系统还为调度器提供节拍计数，用于实现线程时间片。时间片不能直接表示为全局超时：它不是全局到期事件，而是每个 CPU 自己的值。在 SMP 系统中，各 CPU 须分别跟踪。

由于可能没有额外硬件驱动时间片，Zephyr 复用现有定时器驱动。当正在运行的线程采用时间片时，传给 sys_clock_set_timeout() 的值可能被缩短，比当前最近的超时还要小。

保留毫秒 API 的子系统

通常这类代码的迁移与应用代码相同。子系统可以自行处理用户传入的毫秒数，到传给内核时再用 K_MSEC() 转换为内核超时值。

代价是不能使用更高精度的超时构造宏或绝对超时等新功能。对需求简单的子系统，这可能是可以接受的。

一个难点是 K_FOREVER 已不再是整数。过去能把它传给毫秒 API 的子系统如今需要改用其他整数标记来表示“永久”。K_NO_WAIT 也有类型安全问题，但其数值一直是零，迁移方式较直接。

使用 k_timeout_t 的子系统

如果参数表示允许等待多久，应尽可能使用内核原生超时抽象。但 k_timeout_t 是不透明类型，应用须先转换才能检查它。

某些判断非常简单。需要检测 K_FOREVER 时，可用 K_TIMEOUT_EQ() 宏比较不透明结构是否相等，再作特殊处理。

更复杂的场景是：子系统收到一个超时，在循环中边处理边等待，其间可能多次调用阻塞式内核操作。考虑下面的设计：

void my_wait_for_event(struct my_subsys *obj, int32_t timeout_in_ms)
{
    while (true) {
        uint32_t start = k_uptime_get_32();

        if (is_event_complete(obj)) {
            return;
        }

        /* Wait for notification of state change */
        k_sem_take(obj->sem, timeout_in_ms);

        /* Subtract elapsed time */
        timeout_in_ms -= (k_uptime_get_32() - start);
    }
}

这段代码需要检查超时值的内部表示，现在已不可行。内部函数 sys_timepoint_calc() 和 sys_timepoint_timeout() 可以在任意超时与时间点之间转换；时间点以超时到期时的运行节拍表示。因此循环可以改写为：

void my_wait_for_event(struct my_subsys *obj, k_timeout_t timeout)
{
    /* Compute the end time from the timeout */
    k_timepoint_t end = sys_timepoint_calc(timeout);

    do {
        if (is_event_complete(obj)) {
            return;
        }

        /* Update timeout with remaining time */
        timeout = sys_timepoint_timeout(end);

        /* Wait for notification of state change */
        k_sem_take(obj->sem, timeout);
    } while (!K_TIMEOUT_EQ(timeout, K_NO_WAIT));
}

sys_timepoint_calc() 可接受 K_FOREVER 和 K_NO_WAIT，也同样适用于绝对超时和常规超时。反过来，若创建时间点时使用了特殊值，sys_timepoint_timeout() 可返回 K_FOREVER 或 K_NO_WAIT；时间点已过去时也返回后者。简单判断还可使用 sys_timepoint_expired()。

使用这些工具仍须小心。相对超时的参照时刻是调用 sys_timepoint_calc() 时，而调用者预期的是自己传入超时的时刻。因此应尽量在用户代码创建超时的同时调用该函数，且只调用一次。不要拿之前存储的超时值来调用它，更不要在循环中反复调用。
