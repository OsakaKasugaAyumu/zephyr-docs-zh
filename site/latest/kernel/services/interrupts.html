中断（Interrupts）

非官方简体中文译本 · E03 · 英文基线 4.5.99 · 全站目录（94 篇） · E 批目录 · 本页英文原文

中断服务程序（interrupt service routine）（ISR）是异步响应硬件或软件中断的函数。ISR 通常抢占当前线程，以很低的延迟作出响应。只有全部 ISR 工作完成后，线程才恢复执行。

基本概念

在底层硬件允许的范围内，可以定义任意数量的 ISR，数量只受可用 RAM 限制。

ISR 有以下关键属性：

  • 触发 ISR 的中断请求（IRQ）信号。

  • 与 IRQ 关联的优先级。

  • 用来处理中断的中断服务程序（interrupt service routine）。

  • 传递给该函数的参数值。

通过中断描述符表（IDT）或向量表，将特定中断源与 ISR 关联起来。在任一时刻，一个特定 IRQ 只能直接关联一个 ISR。

多个 ISR 可以共用一个处理函数。这样，同一个函数既能处理一个设备的多种中断，也能服务多个通常同类型的设备。传入的参数值让函数区分是哪一个中断到来。

对所有未使用的 IDT 表项，内核都提供默认 ISR。如果出现意外中断，该 ISR 会触发致命系统错误。

内核支持中断嵌套（interrupt nesting）。执行 ISR 期间若出现更高优先级中断，它可抢占当前 ISR；高优先级 ISR 处理完成后，低优先级 ISR 恢复执行。

ISR 在内核的中断上下文（interrupt context）中执行。该上下文有专用栈区（某些架构上有多个）。若支持嵌套中断，中断栈必须足以容纳多个嵌套执行的 ISR。

重要

许多内核 API 只能由线程使用，不能在 ISR 中调用。如果一段代码可在两种上下文中运行，可用 k_is_in_isr() 判断当前是否位于 ISR，并据此调整行为。

多级中断处理

硬件平台可通过一个或多个级联中断控制器，支持超过原生数量的中断线。多个硬件中断源汇合到一条线路上，再接入上一级控制器。

若支持级联中断控制器，应启用 CONFIG_MULTI_LEVEL_INTERRUPTS，并根据硬件架构配置 CONFIG_2ND_LEVEL_INTERRUPTS 和 CONFIG_3RD_LEVEL_INTERRUPTS。

为每个中断分配唯一的 32 位编号，编号中包含选择并调用正确 ISR 所需的信息。按图示编码，每级占一个字节，最多支持四级中断。

└───┴───┴─│─┴───┴───┴───┴───┴───┴───┴─│─┴───┴───┘
          └─────────────────┐         └─────────────────────┐
      5                     v                               v
┌───┬───┬───┬───┬───┬───┬───┐   ┌───┬───┬───┬───┬───┬───┬───┐

此图展示了三级中断。

  • 每格代表一条中断线，从最右边的 0 开始编号。

  • 第一级有 12 条线，其中第 2、9 号线连接下一级控制器，设备 A 接在第 4 号线上。

  • 一个第二级控制器的第 5 号线连接第三级控制器，设备 C 接在第 3 号线上。

  • 另一个第二级控制器没有下级控制器，设备 B 接在第 2 号线上。

  • 第三级控制器的第 2 号线连接设备 D。

以图中的 A、B、C、D 四个中断为例，下面说明如何为每个硬件中断生成唯一编号：

A -> 0x00000004
B -> 0x00000302
C -> 0x00000409
D -> 0x00030609

说明

从第二级开始，线号在编码时加 1，因为 0 表示该级没有中断。设备 D 接在第三级的第 2 号线；该控制器接入第二级第 5 号线，后者接入第一级第 9 号线（2 → 5 → 9）。计入偏移后，D 的编号是 0x00030609。

防止中断打断执行

在执行对时间敏感的操作或临界区操作时，当前线程有时需要防止 ISR 执行。

线程可使用IRQ 锁（IRQ lock）暂时阻止系统处理所有常规 IRQ。锁可以嵌套，因此调用方不必预先知道它是否已被持有。加锁几次就必须对应解锁几次，内核才能在线程运行时恢复处理中断。

重要

持有 IRQ 锁的线程不得休眠；只能调用标有 isr-ok 的函数。

线程也可暂时禁用指定 IRQ，使其信号到来时不执行相应 ISR。随后必须将此 IRQ 重新启用，才能再次执行 ISR。

重要

禁用某个 IRQ 后，系统中所有线程都不会被相应 ISR 抢占，而不仅限于禁用它的线程。

零延迟中断（zero-latency interrupts）

通过 IRQ 锁防止打断可能增大实际中断延迟。某些低延迟应用无法接受这种延迟。

内核允许对延迟要求严格的中断使用 IRQ 锁也无法屏蔽的优先级，这就是零延迟中断。须启用 CONFIG_ZERO_LATENCY_IRQS，并将中断声明为直接 ISR（direct ISR），且不得在其中使用 ISR_DIRECT_PM，因为常规 ISR 会与内核交互。针对该中断，还须将标志 IRQ_ZERO_LATENCY 传给 IRQ_DIRECT_CONNECT 宏。有些架构允许零延迟 ISR 既是直接的也是动态的，见定义直接 ISR。

零延迟中断应直接处理硬件事件，不应与内核代码交互。在此上下文调用任何内核 API 均应视为行为未定义；若仍这样做，应用必须自行验证行为正确。零延迟中断不得修改常规 Zephyr 上下文调用内核 API 时会检查的数据，也不得引发需要同步处理的异常（如 kernel panic）。

如果系统电源管理（PM）在恢复期间保持中断锁定，零延迟中断不受这一恢复顺序约束。它可能在挂起或恢复逻辑中、PM 状态记录和 SoC／设备硬件恢复完成之前执行。ISR 必须能在这种唤醒阶段安全运行；否则，当系统状态不允许它执行时，必须屏蔽或禁用该中断源。当设备路径可能产生零延迟中断时，如何禁止策略选取不安全的电源状态，见设备电源策略约束。

重要

是否支持零延迟中断取决于架构。目前已在 ARM Cortex-M 架构变体中实现。

提示

为降低闪存访问延迟，可考虑将 ISR 及所有相关符号移至 RAM。

将 ISR 的工作移交给线程

为使系统行为可预测，ISR 应尽快返回。耗时处理应部分或全部移交给线程，以恢复内核响应其他中断的能力。

内核提供多种将中断相关处理移交给线程的机制。

  • ISR 可通过 FIFO、LIFO 或信号量等内核对象通知辅助线程执行相关工作。

  • ISR 可要求系统工作队列线程执行工作项，见工作队列线程。

ISR 移交工作后，通常只需在退出时切换一次上下文，目标线程便能几乎立即接手。但这取决于其优先级：当前的协作式线程或其他高优先级线程可能先运行。

共享中断线

一些硬件平台上的多个 IP 模块共用一条中断线。例如，中断 17 可由 DMA 控制器用来报告传输完成，也可由 DAI 控制器用来报告传输 FIFO 达到水位。逐一编写特殊逻辑或采用变通方案（如 shared_irq 中断控制器）不易扩展。

可用 CONFIG_SHARED_INTERRUPTS 启用共享中断。通过 IRQ_CONNECT 或 irq_connect_dynamic() 在同一条线上注册第二组 ISR 和参数时，该线成为共享线。此后每次触发都会用各自的参数调用两个 ISR。共用一条线的实体称为客户端；CONFIG_SHARED_IRQ_MAX_NUM_CLIENTS 控制每条线最多允许多少个客户端。

中断共享对使用者是透明的。仍可按通常方式用 IRQ_CONNECT 和 irq_connect_dynamic() 注册，底层负责处理共享。

同时开启共享和动态中断支持后，可用 irq_disconnect_dynamic() 动态断开 ISR。断开后，即使原中断线再次触发，也不会再调用该 ISR。

启用 CONFIG_SHARED_INTERRUPTS 会使二进制文件明显增大，请谨慎使用。

实现

定义常规 ISR

在运行时调用 IRQ_CONNECT 定义 ISR，再调用 irq_enable() 启用它。

说明

irq_enable()、irq_lock() 等无前缀名称是旧写法。新代码应使用带命名空间的 k_irq_enable()、k_irq_lock() 等。旧名称仍受完整支持。

重要

IRQ_CONNECT() 不是 C 函数，底层使用内联汇编，所有实参都须在构建时已知。支持多个实例的驱动可能需要为每个实例定义配置函数，分别设置中断。

下例定义并启用一个 ISR。

#define MY_DEV_IRQ  24       /* device uses IRQ 24 */
#define MY_DEV_PRIO  2       /* device uses interrupt priority 2 */
/* argument passed to my_isr(), in this case a pointer to the device */
#define MY_ISR_ARG  DEVICE_GET(my_device)
#define MY_IRQ_FLAGS 0       /* IRQ flags */

void my_isr(void *arg)
{
   ... /* ISR code */
}

void my_isr_installer(void)
{
   ...
   IRQ_CONNECT(MY_DEV_IRQ, MY_DEV_PRIO, my_isr, MY_ISR_ARG, MY_IRQ_FLAGS);
   irq_enable(MY_DEV_IRQ);
   ...
}

IRQ_CONNECT 宏的全部参数必须在构建时确定；有些场景无法满足这一要求。可用 irq_connect_dynamic() 在运行时安装中断，其用法与 IRQ_CONNECT 相同：

void my_isr_installer(void)
{
   ...
   irq_connect_dynamic(MY_DEV_IRQ, MY_DEV_PRIO, my_isr, MY_ISR_ARG,
                       MY_IRQ_FLAGS);
   irq_enable(MY_DEV_IRQ);
   ...
}

动态中断需要启用 CONFIG_DYNAMIC_INTERRUPTS。此处所述动态中断目前不支持移除或重新配置。

定义直接 ISR

常规 Zephyr 中断会带来一些开销，某些低延迟场景可能无法接受。具体如下：

  • 取出 ISR 的参数并传给 ISR。

  • 若启用了电源管理且系统原来处于空闲状态，须先将所有硬件从低功耗状态恢复，再执行 ISR，这可能很耗时。

  • 部分架构由硬件切换到中断栈；其他架构需要由软件切换。

  • 中断处理结束后，操作系统还会执行逻辑，判断是否需要重新调度。

  • 零延迟中断必须声明为直接 ISR，因为常规 ISR 会与内核交互。

Zephyr 支持“直接”中断：用 IRQ_DIRECT_CONNECT 安装，用 ISR_DIRECT_DECLARE 声明处理程序。其实现有特殊要求，可用功能也更少；详见 IRQ_DIRECT_CONNECT 和 ISR_DIRECT_DECLARE 的定义。

只有选择了 CONFIG_ARCH_HAS_DIRECT_INTERRUPTS 的架构支持直接中断。在其他架构上使用 IRQ_DIRECT_CONNECT 或 ISR_DIRECT_DECLARE 会导致构建失败。

下例展示直接 ISR：

#define MY_DEV_IRQ  24       /* device uses IRQ 24 */
#define MY_DEV_PRIO  2       /* device uses interrupt priority 2 */
#define MY_IRQ_FLAGS 0       /* IRQ flags */

ISR_DIRECT_DECLARE(my_isr)
{
   do_stuff();
   /* PM done after servicing interrupt for best latency. This cannot be
   used for zero-latency IRQs because it accesses kernel data. */
   ISR_DIRECT_PM();
   /* Ask the kernel to check if scheduling decision should be made. If the
   ISR is for a zero-latency IRQ then the return value must always be 0. */
   return 1;
}

void my_isr_installer(void)
{
   ...
   IRQ_DIRECT_CONNECT(MY_DEV_IRQ, MY_DEV_PRIO, my_isr, MY_IRQ_FLAGS);
   irq_enable(MY_DEV_IRQ);
   ...
}

动态安装直接中断的能力取决于架构。目前 Arm Cortex-M 通过 ARM_IRQ_DIRECT_DYNAMIC_CONNECT 宏支持将中断声明为既直接又动态。

在 RAM 中执行 ISR

为实现极低延迟，可将 ISR 和向量表移到 RAM，消除闪存访问延迟。启用 CONFIG_SRAM_VECTOR_TABLE 和 CONFIG_SRAM_SW_ISR_TABLE 可将表放入 RAM，再使用 Zephyr 的代码与数据重定位机制将 ISR 代码及相关符号也移入 RAM。

共享一条中断线

下例为同一中断号定义两个 ISR。

#define MY_DEV_IRQ 24               /* device uses INTID 24 */
#define MY_DEV_IRQ_PRIO 2           /* device uses interrupt priority 2 */
/*  this argument may be anything */
#define MY_FST_ISR_ARG INT_TO_POINTER(1)
/*  this argument may be anything */
#define MY_SND_ISR_ARG INT_TO_POINTER(2)
#define MY_IRQ_FLAGS 0              /* IRQ flags */

void my_first_isr(void *arg)
{
   ... /* some magic happens here */
}

void my_second_isr(void *arg)
{
   ... /* even more magic happens here */
}

void my_isr_installer(void)
{
   ...
   IRQ_CONNECT(MY_DEV_IRQ, MY_DEV_IRQ_PRIO, my_first_isr, MY_FST_ISR_ARG, MY_IRQ_FLAGS);
   IRQ_CONNECT(MY_DEV_IRQ, MY_DEV_IRQ_PRIO, my_second_isr, MY_SND_ISR_ARG, MY_IRQ_FLAGS);
   ...
}

定义常规 ISR一节所述对 IRQ_CONNECT 的限制在此仍适用。若禁用 CONFIG_SHARED_INTERRUPTS，上述代码会构建失败；否则，中断 24 每次触发时都将调用这两个 ISR。

若 CONFIG_SHARED_IRQ_MAX_NUM_CLIENTS 小于 2（本例的客户端数），构建会报错。

启用动态中断后，可用 irq_connect_dynamic() 在运行时共享中断。若超过配置的最大客户端数，会触发断言失败。

动态断开 ISR

下例为同一中断号定义两个 ISR，并在运行时断开第二个。

#define MY_DEV_IRQ 24               /* device uses INTID 24 */
#define MY_DEV_IRQ_PRIO 2           /* device uses interrupt priority 2 */
/*  this argument may be anything */
#define MY_FST_ISR_ARG INT_TO_POINTER(1)
/*  this argument may be anything */
#define MY_SND_ISR_ARG INT_TO_POINTER(2)
#define MY_IRQ_FLAGS 0              /* IRQ flags */

void my_first_isr(void *arg)
{
   ... /* some magic happens here */
}

void my_second_isr(void *arg)
{
   ... /* even more magic happens here */
}

void my_isr_installer(void)
{
   ...
   IRQ_CONNECT(MY_DEV_IRQ, MY_DEV_IRQ_PRIO, my_first_isr, MY_FST_ISR_ARG, MY_IRQ_FLAGS);
   IRQ_CONNECT(MY_DEV_IRQ, MY_DEV_IRQ_PRIO, my_second_isr, MY_SND_ISR_ARG, MY_IRQ_FLAGS);
   ...
}

void my_isr_uninstaller(void)
{
   ...
   irq_disconnect_dynamic(MY_DEV_IRQ, MY_DEV_IRQ_PRIO, my_first_isr, MY_FST_ISR_ARG, MY_IRQ_FLAGS);
   ...
}

调用 irq_disconnect_dynamic() 后，中断 24 不再共享，效果就像从未执行第一次 IRQ_CONNECT 调用。只有启用了 CONFIG_DYNAMIC_INTERRUPTS 才支持这种行为，否则会产生链接错误。

实现细节

构建时使用专门工具生成中断表。以下说明适用于除 x86 之外的所有架构；x86 的情况见后面的x86 实现细节。

调用 IRQ_CONNECT 会声明一个 struct _isr_list 实例并放入专用的 .intList 段。该段只在预编译阶段存在，供 Zephyr 脚本生成中断表，最终构建会移除它。脚本提供不同解析器，以处理该段的数据并生成所需输出。

默认解析器直接从 .intList 表项提取地址，生成保存参数和中断处理程序的 C 数组。除上述例外，它适用于所有架构和编译器。其限制是：数组生成后，代码地址不得再变化。若此时发生重定位，表项可能不再指向预期函数。因此，这种兼容性较好的方式限制了链接时优化（LTO）的使用。

本地 ISR 声明解析器采用另一种方法，在二进制层面构造相同的数组。每个表项都直接在使用 IRQ_CONNECT 的文件中声明和定义，放入名称唯一、自动生成的段。段名写入 .intList，工具再生成链接脚本片段，将表项放到正确地址。这种解析器仅适用于受支持的架构和工具链，但会为链接器保留对象间关系，使 LTO 成为可能。

使用 C 数组实现

这是 Zephyr 支持的各架构均可使用的默认配置。

每次调用 IRQ_CONNECT 都会声明一个 struct _isr_list 实例，并放入专用 .intList 段：

struct _isr_list {
    /** IRQ line number */
    int32_t irq;
    /** Flags for this IRQ, see ISR_FLAG_* definitions */
    int32_t flags;
    /** ISR to call */
    void *func;
    /** Parameter for non-direct IRQs */
    void *param;
};

Zephyr 分两个阶段构建。第一阶段生成 ${ZEPHYR_PREBUILT_EXECUTABLE}.elf，包含 .intList 全部表项，前面带有以下表头：

struct {
    void *spurious_irq_handler;
    void *sw_irq_handler;
    uint32_t num_isrs;
    uint32_t num_vectors;
    struct _isr_list isrs[];  <- of size num_isrs
};

gen_isr_tables.py 使用 ${ZEPHYR_PREBUILT_EXECUTABLE}.elf 中的表头和 struct _isr_list 实例生成 C 文件，在其中定义向量表及软件 ISR 表，再编译并链接到最终应用。

中断优先级不编码在这些表中。IRQ_CONNECT 还包含运行时逻辑，用于向中断控制器写入所需优先级。若架构没有中断优先级的概念，此参数会被忽略。

向量表（Vector Table）

启用 CONFIG_GEN_IRQ_VECTOR_TABLE 时生成向量表。CPU 直接使用这个函数指针数组：第 n 项对应第 n 条 IRQ 线的处理程序。具体如下：

  1. 对用 IRQ_DIRECT_CONNECT 声明的直接中断，该处存放处理函数。

  2. 对用 IRQ_CONNECT 声明的常规中断，该处存放公共软件 IRQ 处理程序的地址。公共代码负责内核中断状态管理，并从软件 ISR 表查找 ISR 及其参数。

  3. 对未配置的中断线，该处存放意外 IRQ 处理程序的地址。一旦调用它，就会产生致命系统错误。

某些架构的所有中断共用一个入口，不支持向量表；此时应禁用 CONFIG_GEN_IRQ_VECTOR_TABLE。

有些架构把起始向量保留给系统异常，另用一张表声明它们。此时需设置 CONFIG_GEN_IRQ_START_VECTOR，使表索引具有正确偏移。

软件 ISR 表

这是一个 struct _isr_table_entry 数组：

struct _isr_table_entry {
    void *arg;
    void (*isr)(void *);
};

公共软件 IRQ 处理程序从中断控制器寄存器读取当前 IRQ 线号，以它为索引查找 ISR 及参数，然后执行 ISR。

共享软件 ISR 表

这是一个 struct z_shared_isr_table_entry 数组：

struct z_shared_isr_table_entry {
    struct _isr_table_entry clients[CONFIG_SHARED_IRQ_MAX_NUM_CLIENTS];
    size_t client_num;
};

此表记录各中断线上已注册的客户端。中断线开始共享时，z_shared_isr() 会替换 _sw_isr_table 中当前注册的 ISR；这个特殊 ISR 会遍历客户端列表，调用各自的 ISR。

使用链接脚本实现

通过准备和解析 .isrList 段来构建中断向量数组的方法称为“本地 ISR 声明”：各数组表项直接在调用 IRQ_CONNECT 宏的位置创建，再用自动生成的链接脚本放入正确的内存位置。

选择 CONFIG_ISR_TABLES_LOCAL_DECLARATION 可启用该方式。如果架构和工具链支持此配置，会设置 CONFIG_ISR_TABLES_LOCAL_DECLARATION_SUPPORTED；见该选项的说明，了解目前支持哪些配置。

每次调用 IRQ_CONNECT 或 IRQ_DIRECT_CONNECT 都会声明一个 struct _isr_list_sname 实例并放入专用 .intList 段：

struct _isr_list_sname {
    /** IRQ line number */
    int32_t irq;
    /** Flags for this IRQ, see ISR_FLAG_* definitions */
    int32_t flags;
    /** The section name */
    const char sname[];
};

段名存放于柔性数组成员中，因此初始化后的结构体大小随名称长度而变。构建时脚本使用完整表项，其中含有正确放置中断所需的全部信息。

除 _isr_list_sname 外，IRQ_CONNECT 宏还会生成一个中断数组表项：

struct _isr_table_entry {
    const void *arg;
    void (*isr)(const void *);
};

该数组放在一个段内，段名记录在 _isr_list_sname 结构中。

IRQ_DIRECT_CONNECT 宏生成的值取决于架构：可以是指向中断处理程序的变量：

static uintptr_t <unique name> = ((uintptr_t)func);

也可以是不带函数序言和尾声的裸函数，直接跳转到中断处理程序：

static void <unique name>(void)
{
    __asm(ARCH_IRQ_VECTOR_JUMP_CODE(func));
}

与 IRQ_CONNECT 类似，新变量或函数会放在指定的段内，段的信息保存在 _isr_list_sname 中。

脚本生成的文件

中断表生成脚本创建三个文件：isr_tables.c、isr_tables_swi.ld 和 isr_tables_vt.ld。

isr_tables.c 包含中断、直接中断和已启用的共享中断所需的结构。它只定义应用没有实现的结构；对于在其他位置实现的中断，则用注释指出位置。

另外还有两个链接文件：在架构要求放置中断向量的位置引入 isr_tables_vt.ld；isr_tables_swi.ld 描述软件中断表元素的布局。分开生成是因为软件表可根据配置放在可写段或只读段。

x86 实现细节

x86 的中断描述符表（IDT）是一种特殊的向量表，布局必须符合处理器文档。arch/x86/gen_idt.py 用 .intList 段生成该表。在基于 APIC 的系统上，向量索引不等于 IRQ 线号。前 32 个向量保留给 CPU 异常，其余向量直到索引 255，每 16 个对应一个优先级：优先级 0 使用向量 32–47，优先级 1 使用 48–63，依此类推。arch/x86/gen_idt.py 构造 IDT 时，为每个中断在请求的优先级区间内查找空闲向量，并设置相应处理程序。

在 x86 上，CPU 执行中断或异常向量时，没有绝对可靠的办法判断触发了哪个向量，所以不使用按 IRQ 线号索引的软件 ISR 表。IRQ_CONNECT 生成一小段汇编，用 ISR 及其参数调用 _interrupt_enter() 中的公共中断代码。IDT 中存放这段汇编入口桩的地址。对用 IRQ_DIRECT_CONNECT 声明的中断，IDT 直接存放不带参数的 ISR。

在向量位置对应中断优先级的系统上，中断控制器在运行时必须知道 IRQ 线对应哪个向量。arch/x86/gen_idt.py 另生成 _irq_to_interrupt_vector 数组，将 IRQ 线映射到配置的 IDT 向量。运行时 IRQ_CONNECT 用它为中断控制器设置该关联。

对动态中断，构建时每个使用中的中断都要生成一个 4 字节的入口桩。桩数由 CONFIG_X86_DYNAMIC_IRQ_STUBS 控制。每个桩将唯一标识压栈，再用该标识从连接动态中断时填充的表中取出处理函数和参数。

超出默认支持的中断数量

多级中断配置默认用每级 8 位的掩码确定中断编码属于哪一级。若某个汇聚器支持超过 255 个中断，可能需要自定义各级位数。所有级别使用的位数总和不得超过 32，以便装入一个 32 位整数。要覆盖 Kconfig.multilevel 中的默认值 8，可用 CONFIG_1ST_LEVEL_INTERRUPT_BITS、CONFIG_2ND_LEVEL_INTERRUPT_BITS、CONFIG_3RD_LEVEL_INTERRUPT_BITS 分别设置第一、第二、第三级。这些设置决定生成中断值、判断级别和级别转换时使用的掩码长度与位移。逻辑见 irq_multilevel.h。

建议用法

对必须快速响应、能迅速完成且不阻塞的操作，可用常规或直接 ISR。

说明

对耗时或可能阻塞的中断处理，应移交线程。可用的技术见将 ISR 的工作移交给线程。
