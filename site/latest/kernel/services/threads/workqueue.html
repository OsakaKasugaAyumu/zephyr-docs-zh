工作队列线程

工作队列（workqueue）是一种内核对象，用专门的线程按先进先出的顺序处理工作项（work item）。处理时调用各工作项指定的函数。中断服务程序（ISR）或高优先级线程通常用工作队列将不紧急的任务交给较低优先级的线程，以免影响时间敏感的操作。

工作队列的数量只受可用 RAM 限制。每个队列通过其内存地址引用。

工作队列有以下主要属性：

  • 一个队列，保存已经提交但尚未处理的工作项；

  • 一个负责处理队列中工作项的线程（thread）。可配置其优先级，按需要使用协作式或可抢占的线程。

不管优先级如何，工作队列线程在逐个处理已提交工作项的间隙会让出 CPU，以免协作式工作队列让其他线程一直得不到运行机会。

工作队列必须先初始化才能使用。初始化会清空队列并创建处理线程。线程持续运行，没有工作项时休眠。

工作项的生命周期

可以定义任意多个工作项（work items），每项都通过其内存地址引用。

每个工作项都有一个处理函数（handler function），由工作队列线程在处理该项时调用。函数只接收一个参数，即工作项自身的地址。工作项还保存自己的状态信息。

工作项必须先初始化才能使用。初始化时会记录其处理函数，并将其标记为无待处理工作。

ISR 或线程可将工作项提交给工作队列，使其入队（queued）（K_WORK_QUEUED）。提交会把它追加到队尾。队列线程处理完前面所有工作项后，取出下一项并调用其处理函数。等待时间既取决于线程调度优先级，也取决于前面工作项的工作量；可能很快执行，也可能排队很久。

可延迟工作项可被安排延迟提交（scheduled）到工作队列（K_WORK_DELAYED），见可延迟工作。

工作项在队列线程上执行时处于运行中（K_WORK_RUNNING）状态；若它已开始执行，随后有线程请求取消，它也可能同时处于正在取消（K_WORK_CANCELING）状态。

一个工作项可以同时处于多种状态，例如：

  • 正在一个工作队列上执行；

  • 标记为正在取消（因为某线程通过 k_work_cancel_sync() 正在等待工作项结束）；

  • 已在同一队列中排队等待再次执行；

  • 已被安排在稍后提交到某队列（可能是另一个队列）。

上述情形可以同时成立。处于这些状态中任意一种的工作项可称为待处理（pending）（k_work_is_pending()）或忙（busy）（k_work_busy_get()）。

处理函数可以使用任何线程可用的内核 API，但必须慎用可能阻塞的操作（如获取信号量）。当前处理函数返回前，这个工作队列无法处理后续工作项。

如果不需要，可忽略处理函数的唯一参数。若需要其他数据，可将工作项嵌入更大的结构体，再对收到的工作项指针使用 CONTAINER_OF 求得外围结构体地址，由此访问附加数据。

通常只需初始化工作项一次，之后每当需要执行相应工作时就将其提交到指定队列。若 ISR 或线程重复提交一个已经排队的工作项，该项位置不变，也不会多执行一次。

处理函数可以把自己正在处理的工作项重新提交；此时它已经出队。这样可分阶段完成工作，而不至于过度推迟队列中其他工作项。

重要

工作队列线程处理完待处理工作项之前，不得修改该项。这意味着工作项处于忙状态时不得重新初始化；处理函数执行完毕前，也不得修改它工作所需的附加信息。

可延迟工作

ISR 或线程有时不希望工作项立即执行，而希望在一段时间之后才处理。这时可调度一个可延迟工作项（delayable work item），使其在未来某个时刻提交到队列。

可延迟工作项包含一个普通工作项，并有额外字段记录应在何时、向哪个队列提交。

初始化和安排可延迟工作项的方式与普通工作项相似，但使用不同的内核 API。调度请求会启动超时机制；指定延迟结束时，内核才将工作项提交给指定队列，随后按正常方式排队处理。

注意：可延迟工作项的处理函数收到的仍是底层普通工作结构体的指针，不能从 k_work_delayable 的公开接口直接访问该成员。要取得包含可延迟工作项的对象，请使用以下写法：

static void work_handler(struct k_work *work)
{
        struct k_work_delayable *dwork = k_work_delayable_from_work(work);
        struct work_context *ctx = CONTAINER_OF(dwork, struct work_context,
                                                timed_work);
        ...

事件触发的工作

k_work_poll_submit() 可安排由轮询事件（poll event）触发的工作项（见轮询 API）。当被监视的资源可用、轮询信号被置位或超时发生时，调用用户定义的函数。与 k_poll() 不同，这种方式不需要专门的线程来等待或主动轮询事件。

触发式工作项是增加了以下属性的普通工作项：

  • 指向轮询事件数组的指针；这些事件会触发工作项提交至队列；

  • 该事件数组的大小。

触发式工作项的初始化和提交方式与普通工作项类似，但使用专用 API。收到提交请求后，内核开始监视事件所指定的内核对象。只要至少有一个对象状态变化，工作项就会提交到指定队列，按通常方式等待处理。

重要

从提交开始，直到工作项执行或取消，触发式工作项及其引用的轮询事件数组都必须保持有效，不能修改。

只要已提交的触发式工作项仍在等待轮询事件，ISR 或线程就可以取消它。这样内核会停止等待关联事件，不会执行工作项。若已过这个阶段，就不能再以此方式取消。

系统工作队列

内核定义了一个称为系统工作队列（system workqueue）的队列，任何需要工作队列的应用或内核代码均可使用。它是可选的；只有应用用到它时才存在。

重要

每个额外工作队列都会显著增加内存开销。因此应先考虑系统工作队列，仅在无法共用时才另建。例如，新工作项会阻塞，导致系统工作队列中的其他任务出现不可接受的延迟，此时就适合单独建队列。

注意：系统工作队列默认处于最低的协作式优先级，所以它在排空队列时优先于所有可抢占线程。贸然将其改为可抢占优先级有风险，因为子系统或驱动可能默认工作项在协作式上下文中执行。低优先级任务可以使用独立的低优先级队列。

如何使用工作队列

定义和控制工作队列

用 k_work_q 类型变量定义工作队列。先定义工作线程的栈区，再将 k_work_q 清零或调用 k_work_queue_init() 初始化，最后调用 k_work_queue_start()。栈区须用 K_THREAD_STACK_DEFINE 定义，以确保内存布局正确。

以下代码定义并初始化一个工作队列：

#define MY_STACK_SIZE 512
#define MY_PRIORITY 5

K_THREAD_STACK_DEFINE(my_stack_area, MY_STACK_SIZE);

struct k_work_q my_work_q;

k_work_queue_init(&my_work_q);

k_work_queue_start(&my_work_q, my_stack_area,
                   K_THREAD_STACK_SIZEOF(my_stack_area), MY_PRIORITY,
                   NULL);

还可以通过最后一个可选参数设置队列标识及线程重新调度的部分行为，详见 k_work_queue_start()。

可使用以下 API 操作工作队列：

  • k_work_queue_drain() 可阻塞调用线程，直到队列中不再有工作项。排空期间仍接受该队列线程自身重新提交的工作，但拒绝其他线程和 ISR 提交的工作。还可以在排空后继续封住队列（plug），使调用线程能在此期间完成其他工作。排空本身不影响可延迟工作项的调度或处理；但若到期提交时队列仍被封住，该项会提交失败，且不会通知调用方。

  • k_work_queue_unplug() 解除此前排空操作施加的提交限制。

提交工作项

用 k_work 类型的变量定义工作项。通常须调用 k_work_init() 初始化；若用 K_WORK_DEFINE 定义，则已在编译时完成初始化。

调用 k_work_submit() 将初始化后的工作项提交到系统工作队列；调用 k_work_submit_to_queue() 则提交到指定队列。

以下示例让 ISR 将错误消息的打印交给系统工作队列。如果 ISR 在该工作项仍在排队时再次提交，工作项不会改变，因此新产生的那条错误消息不会打印。

struct device_info {
    struct k_work work;
    char name[16]
} my_device;

void my_isr(void *arg)
{
    ...
    if (error detected) {
        k_work_submit(&my_device.work);
    }
    ...
}

void print_error(struct k_work *item)
{
    struct device_info *the_device =
        CONTAINER_OF(item, struct device_info, work);
    printk("Got error on device %s\n", the_device->name);
}

/* initialize name info for a device */
strcpy(my_device.name, "FOO_dev");

/* initialize work item for printing device's error messages */
k_work_init(&my_device.work, print_error);

/* install my_isr() as interrupt handler for the device (not shown) */
...

以下 API 可用于查询状态或与工作项同步：

  • k_work_busy_get() 返回反映工作项状态的标志位快照。零表示它既未被调度、也未提交或执行，工作队列机制也未再以其他方式引用它。

  • k_work_is_pending() 是辅助函数，当且仅当工作项已被安排、入队或正在运行时返回 true。

  • 线程可以调用 k_work_flush()，阻塞到该项工作完成。如果没有待处理工作，则立即返回。

  • k_work_cancel() 尝试阻止工作项执行，但不保证成功；ISR 可以安全调用。

  • 线程可调用 k_work_cancel_sync()，等待工作结束。如果取消成功或无需取消（工作未提交且未运行），则立即返回。ISR 调用 k_work_cancel() 后，线程可借此确认取消操作已完成。

调度可延迟工作项

用 k_work_delayable 类型的变量定义可延迟工作项，并调用 k_work_init_delayable() 初始化。

延迟工作有两种常见策略，区别在于新事件到来时是否顺延截止时间。例如，异步收集来自键盘 UART 的字符。下面两类 API 都能延迟提交工作：

  • k_work_schedule()（或 k_work_schedule_for_queue()）将工作安排在指定时刻或延迟后执行。在原延迟结束前，用同一 API 再次调度不会改变提交时间。若策略是从收到第一份尚未处理的数据开始计时，在固定时长内继续收集，就用此方式；

  • k_work_reschedule()（或 k_work_reschedule_for_queue()）无条件设置新的截止时间，覆盖尚未结束的延迟，并可按需更换目标队列。若策略是自最后一份尚未处理的数据到达起，再等待固定时长，就用此方式。

若尚未被调度，两种 API 的行为相同。指定 K_NO_WAIT 会像直接向目标队列提交一样立即入队，无须等待最短超时；例外是使用 k_work_schedule() 且先前的延迟尚未到期。

两者都提供可以指定目标队列的变体。

给定处理函数收到的 k_work 指针，可以用 k_work_delayable_from_work() 取得外围 k_work_delayable 对象的指针。

还可以用以下 API 查询或同步可延迟工作项：

  • k_work_delayable_busy_get() 是 k_work_busy_get() 对应的可延迟版本。

  • k_work_delayable_is_pending() 是 k_work_is_pending() 对应的可延迟版本。

  • k_work_flush_delayable() 是 k_work_flush() 对应的可延迟版本。

  • k_work_cancel_delayable() 是 k_work_cancel() 对应的可延迟版本；同步取消也有相应的 k_work_cancel_delayable_sync()。

与工作项同步

在任何上下文中都可用 k_work_busy_get() 和 k_work_delayable_busy_get() 查询普通或可延迟工作项的状态。但有些情况需要在提交后同步等待；可在线程上下文中调用 k_work_flush()、k_work_cancel_sync() 或 k_work_cancel_delayable_sync()，阻塞到请求的状态达成。

这些 API 需要一个 k_work_sync 对象来提供同步所需的内部对象。它没有供应用检查的成员。如果代码需要在启用 CONFIG_KERNEL_COHERENCE 的架构上运行，就不应在栈上分配此对象。

工作队列使用建议

避免竞态条件

有些数据的传递天然是线程安全的，例如线程把数据放入 k_queue，工作线程再取出处理。但多数情况需要外部同步，以避免工作线程读取或修改另一线程或中断正在访问的共享状态。这可能是表示有工作待办的标志，也可能是 ISR 或线程写入、处理函数读取的对象。

简单的标志可以使用原子操作服务。其他情况可以采用自旋锁（k_spinlock）或线程级同步机制（k_sem、k_mutex 等），避免数据竞态。

如果获取锁可能导致休眠，工作线程一旦睡眠，队列中的其他工作项就得不到执行，而释放该锁可能恰恰依赖它们继续运行。处理函数应尝试以不等待的方式获取锁。例如：

static void work_handler(struct work *work)
{
        struct work_context *parent = CONTAINER_OF(work, struct work_context,
                                                   work_item);

        if (k_mutex_lock(&parent->lock, K_NO_WAIT) != 0) {
                /* NB: Submit will fail if the work item is being cancelled. */
                (void)k_work_submit(work);
                return;
        }

        /* do stuff under lock */
        k_mutex_unlock(&parent->lock);
        /* do stuff without lock */
}

注意：若锁的持有线程优先级低于工作队列，立即反复提交可能使它得不到 CPU，从而无法释放锁，导致应用失效。若确需上述模式，优先使用可延迟工作项，以非零延迟重新调度，给持锁线程运行的机会。

若工作项已被取消，从处理函数再次提交可能失败。这通常可以接受，因为处理函数返回后取消就完成了。若不可接受，上例还需要通过其他途径通知应用工作未完成。

工作项自身的操作已有内部锁；单纯提交或调度不需要外部锁。即使应用使用外部锁保护某个“不要再提交”的标志，只要能保证处理函数最终会取锁并检查是否仍有工作，重新提交就是安全的。如果可延迟工作项因取锁失败而在处理函数里重新调度，就需要其他可独立同步的状态（如取消时由应用或驱动设置的原子标志），以识别取消请求，避免已取消的工作项在延迟到期后再次提交。

检查返回值

工作项 API 会返回底层操作的执行状态。在许多情况下，必须检查返回值，确认是否达到预期效果。

  • 如果工作项正在取消，或队列不再接受新工作，提交（k_work_submit_to_queue()）可能失败。此时该工作不会执行；依赖处理函数推进的子系统可能因此失去响应。

  • 异步取消（k_work_cancel() 或 k_work_cancel_delayable()）返回时，处理函数可能仍在运行。若此时直接操作与处理函数共享的状态，就会出现可能导致故障的数据竞态。

Zephyr 代码中曾出现过许多因不检查操作结果而产生的竞态条件。

有时确实有充分理由认为，结果与预期不同也没有关系。应明确记录：一是将返回值转换为 void，表明是有意忽略；二是说明非预期情况下会怎样。例如：

/* If this fails, the work handler will check pub->active and
 * exit without transmitting.
 */
(void)k_work_cancel_delayable(&pub->timer);

即使如此，后续代码仍须避免数据竞态：它不能保证工作线程此时没有访问相关状态。

不要过早优化

工作队列 API 已设计为可由多个线程和中断安全调用。从外部检查某个工作项的状态并据此决策，反而容易引入新问题。

有了新工作就直接提交。不要先用 k_work_is_pending()、k_work_busy_get() 查状态快照，或通过 k_work_delayable_remaining_get() 判断剩余延迟是否非零，试图借此“优化”提交。这些检查并不可靠：“忙”可能在函数返回时就已过时；多个上下文同时提交时，“不忙”也可能失准。对可延迟工作而言，延迟到期也不代表工作已经结束，它可能仍在队列中或正在运行。

建议在共享状态中维护一个条件，供处理函数确认是否确有工作。这样就能把处理函数用作统一的清理入口；不必在每个提交点分别处理取消和清理，而可以让处理函数自行收尾。

只有在极少数情况下，才能安全地先用 k_work_is_pending() 判断是否需要调用 k_work_flush() 或 k_work_cancel_sync()：必须确信检查期间没有其他上下文会提交该项工作。通常这是因为已持锁，其他上下文不能访问提交所需的状态。

建议用法

可用系统工作队列将复杂的中断相关处理从 ISR 延后到共享线程中。这样既能及时处理相关工作，又不损害系统响应后续中断的能力，也不需要应用另建并管理线程。
