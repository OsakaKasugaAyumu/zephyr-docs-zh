线程（Threads）

本节介绍如何用内核服务创建、调度和删除可以独立执行的线程。

线程（thread）是一种内核对象，用来执行太耗时或太复杂、不宜放在中断服务程序（ISR）中完成的应用任务。

应用可定义任意多个线程，数量只受可用 RAM 限制。创建时分配的线程标识（thread ID）用于引用相应线程。

线程有以下主要属性：

  • 栈区是一块用于存放线程栈的内存。可按线程实际需要指定其大小，并使用专用宏创建和操作该内存区域。

  • 线程控制块（thread control block）供内核内部记录线程元数据，是 k_thread 类型的实例。

  • 线程启动时会调用入口函数，最多可向其传递三个参数值。

  • 调度优先级用于告诉内核调度器如何给线程分配 CPU 时间。（见调度。）

  • 一组线程选项，让内核在特定情况下对线程作特殊处理。（见线程选项。）

  • 启动延迟指定内核在启动线程前应等待多久。

  • 执行模式分为特权模式和用户模式。默认运行在特权模式，可以使用特权指令、访问整个地址空间及外设；用户模式线程的权限较少。是否支持用户模式取决于 CONFIG_USERSPACE。见用户模式。

生命周期

线程创建

线程须先创建才能使用。内核会初始化线程控制块和栈的一端；其余栈空间一般不初始化。

将启动延迟设为 K_NO_WAIT 表示请求立即启动线程。也可以指定超时值，推迟执行，例如等待线程所需的硬件就绪。

延迟启动的线程在开始执行前可被取消；如果已启动，取消请求不生效。成功取消延迟启动的线程须重新创建后才能使用。

启动线程

若以 K_FOREVER 作为启动延迟，线程不会加入调度器的就绪队列，直到显式启动才会执行。调用 k_thread_start() 可启动这样的非活动线程，使其具备被调度的资格；对已启动的线程再次启动没有效果。

这适合先创建线程对象，等应用完成其他设置之后才开始执行的情况。

线程终止

线程启动后通常会持续运行。不过，它也可以从入口函数返回，以同步结束自身的执行。这称为终止（termination）。

线程从入口返回之前，须自行释放持有的共享资源（如互斥锁和动态分配的内存），内核不会自动回收这些资源。

有时一个线程要等另一个线程结束，可调用 k_thread_join()。调用方会阻塞，直到超时、目标线程自行退出，或目标线程因 k_thread_abort() 调用或致命错误而中止。

线程彻底终止后，内核保证不再使用其线程结构体。此时该内存才可复用，例如创建新线程。线程自己发出的“完成”信号可能早于内核收尾：其他线程若收到信号就复用内存，会造成竞态。通常应通过 k_thread_join() 或 k_thread_abort() 同步线程终止状态，而不是依赖应用内部信号。

强制中止线程

线程也可通过中止（aborting）异步结束。如果线程触发致命错误（如解引用空指针），内核会自动将其中止。

线程可调用 k_thread_abort() 中止另一线程或自身。不过，通常应优先通知线程，让它有序释放资源并自行退出，而不是将其强制中止。

和正常终止一样，内核不会回收被中止线程持有的共享资源。

说明

内核目前不保证应用可以重新创建被中止的线程。

挂起线程

线程被挂起（suspended）后，可无限期停止执行。用 k_thread_suspend() 可挂起任何线程，包括调用者自身。再次挂起一个已挂起线程没有额外效果。

挂起的线程不能被调度，直到其他线程调用 k_thread_resume() 来解除挂起。

说明

线程可用 k_sleep() 让自己在指定时间内停止执行。休眠与挂起不同：休眠时间一到，线程便会自动恢复执行资格。

线程状态

当没有任何因素阻止线程执行时，它便处于就绪（ready）状态，有资格被选为当前线程。

若有一个或多个因素阻止线程执行，它就处于未就绪（unready）状态，不能被选为当前线程。

以下情形会使线程未就绪：

  • 线程尚未启动；

  • 线程正在等待一个内核对象完成操作，例如申请当前不可用的信号量；

  • 线程正在等待超时；

  • 线程已被挂起；

  • 线程已终止或中止。

    线程状态与调度转换：从创建、就绪和执行，到等待、挂起、恢复或终止。查看 Zephyr 官网原图

说明

上图看起来似乎将就绪（Ready）与运行中（Running）列为两种独立的线程状态，其实不是。就绪（Ready）是线程状态；运行中（Running）是调度状态，仅适用于就绪（Ready）线程。

线程栈对象

每个线程都需要独立的栈缓冲区，供 CPU 压入上下文。根据配置，线程栈可能还需满足以下约束：

  • 可能需要为内存管理结构额外预留空间。

  • 启用保护区式栈溢出检测时，必须紧挨栈缓冲区之前设置一小段写保护区域，以捕获越界写入。

  • 启用用户空间时，必须另外预留固定大小的提权栈，作为处理系统调用的私有内核栈。

  • 启用用户空间时，线程栈缓冲区的大小和对齐方式必须允许内存保护区域恰好覆盖它。

对齐限制可能很严格。例如，有些 MPU 要求区域大小是 2 的幂，并按区域自身大小对齐。

因此，可移植代码不能把任意字符缓冲区直接传给 k_thread_create()。应使用以 K_KERNEL_STACK 或 K_THREAD_STACK 为前缀的专用宏静态创建栈。

也可用 k_thread_stack_alloc() 动态分配栈，之后通过 k_thread_stack_free() 释放。

仅内核使用的栈

若确定线程绝不会在用户模式下运行，或此栈用于处理中断等特殊上下文，最好用 K_KERNEL_STACK 系列宏定义栈。

这类栈更省内存：无须为栈缓冲区本身设置 MPU 区域，也无须为提权栈或仅用户模式线程需要的内存管理结构额外预留空间。

从用户模式尝试使用这种栈会导致调用者触发致命错误。

未启用 CONFIG_USERSPACE 时，K_THREAD_STACK 系列宏与 K_KERNEL_STACK 系列宏效果相同。

线程栈

如果需要在栈上运行用户线程，或尚无法确定，应使用 K_THREAD_STACK 系列宏。它可能占用更多内存，但栈对象可用于用户线程。

未启用 CONFIG_USERSPACE 时，K_THREAD_STACK 系列宏与 K_KERNEL_STACK 系列宏效果相同。

线程优先级

线程优先级用整数表示，可以为负，也可以非负。数值越小，实际优先级越高。例如，优先级值为 4 的线程 A 比值为 7 的线程 B 优先级更高，而值为 −2 的线程 C 又高于二者。

调度器按优先级将线程分为两类：

  • 协作式线程（cooperative thread）的优先级值为负。一旦成为当前线程，通常会一直执行，直到主动执行某项操作使自己不再就绪。

  • 可抢占线程（preemptible thread）的优先级值非负。若某个协作式线程就绪，或某个同级或更高优先级的可抢占线程就绪，它随时可能被替换。

线程启动后可以提高或降低其优先级。因此，更改优先级可使可抢占线程变为协作式线程，反之亦然。

说明

调度器不会通过启发式算法自行调整优先级。只有应用提出请求时，线程优先级才会被设置或修改。

内核支持的优先级数量实际上没有严格上限。CONFIG_NUM_COOP_PRIORITIES 和 CONFIG_NUM_PREEMPT_PRIORITIES 分别指定两类线程的优先级数量，可用范围如下：

  • 协作式线程：从 −CONFIG_NUM_COOP_PRIORITIES 到 −1；

  • 可抢占线程：从 0 到（CONFIG_NUM_PREEMPT_PRIORITIES − 1）。

线程优先级范围：协作式优先级为负，可抢占优先级非负；数值越小，优先级越高。查看 Zephyr 官网原图

例如，配置 5 级协作式和 10 级可抢占优先级时，范围分别为 −5 至 −1 和 0 至 9。

元中断优先级（Meta-IRQ）

启用 CONFIG_NUM_METAIRQ_PRIORITIES 时，在优先级最高（数值最小）的一端有一类特殊的协作式线程：元中断线程（meta-IRQ thread）。它们按通常优先级调度，但可以抢占所有较低优先级的线程，包括其他元中断线程，即使对方是协作式线程或已锁定调度器。元中断线程仍然是线程，可以被任何硬件中断打断。

说明

若协作式线程（或已锁定调度器的线程）被元中断线程抢占，在后者完成后，只要前者未被挂起或中止，就会在原 CPU 上恢复执行。因此在线程查询其所在 CPU 的属性时，不会意外被迁移到另一 CPU。

因此，让元中断线程解除阻塞（如创建它或调用 k_sem_give()），对较低优先级的调用线程而言效果类似同步系统调用；从真正的中断上下文调用，则类似 Arm 的挂起中断（pended IRQ）。此机制用于驱动子系统的中断下半部（bottom half）或 tasklet 等：线程被唤醒后，保证在当前 CPU 返回应用代码之前运行。

与其他操作系统的某些类似机制不同，元中断线程使用自己按常规方式分配的线程栈，而非每 CPU 的中断栈。在支持的架构上改用 IRQ 栈的设计工作尚未完成。

这打破了 Zephyr 对协作式线程的一般保证（当前线程主动阻塞之前，系统不会调度其他线程）。应用代码使用时须十分谨慎，不能把元中断线程简单当成普通的高优先级线程。

线程选项

内核支持少量线程选项，允许在特定情况下对线程进行特殊处理。选项在线程创建时指定。

不需要选项时，值为零。需要某项功能时按名称指定；多个选项用 | 分隔，即按位或组合。

支持以下线程选项：

K_ESSENTIAL

此选项将线程标记为关键线程（essential thread）。如果该线程终止或被强制中止，内核将其视为致命系统错误。

默认情况下，线程不是关键线程。

K_SSE_REGS

此选项仅适用于 x86，表示线程使用 CPU 的 SSE 寄存器。另见 K_FP_REGS。

默认情况下，内核调度线程时不会尝试保存和恢复这些寄存器。

K_FP_REGS

此选项表示线程使用 CPU 的浮点寄存器。内核需在调度时额外保存和恢复这些寄存器的内容。（详见浮点服务。）

默认情况下，内核在调度线程时不会尝试保存和恢复该寄存器的内容。

K_USER

启用 CONFIG_USERSPACE 时，此标志使线程以权限更少的用户模式创建，见用户模式。否则该标志无效。

K_INHERIT_PERMS

启用 CONFIG_USERSPACE 时，线程继承父线程对所有内核对象的权限，但不包括父线程对象本身。见用户模式。

线程自定义数据

每个线程都有一块 32 位的自定义数据（custom data），只有该线程自己可以访问。应用可以自行规定用途；默认值为零。

说明

ISR 共用一个内核中断处理上下文，因此不能使用线程自定义数据。

默认情况下不启用线程自定义数据。可通过 CONFIG_THREAD_CUSTOM_DATA 开启。

分别用 k_thread_custom_data_set() 和 k_thread_custom_data_get() 写入、读取线程的自定义数据。线程只能访问自己的数据，不能访问其他线程的数据。

以下代码用自定义数据记录各线程调用某个例程的次数。

说明

由于这种方法独占自定义数据槽，一次只适用于一个例程。

int call_tracking_routine(void)
{
    uint32_t call_count;

    if (k_is_in_isr()) {
        /* ignore any call made by an ISR */
    } else {
        call_count = (uint32_t)k_thread_custom_data_get();
        call_count++;
        k_thread_custom_data_set((void *)call_count);
    }

    /* do rest of routine's processing */
    ...
}

可将自定义数据用作指向线程私有数据结构的指针，使例程访问当前线程专属的信息。

线程名称

启用 CONFIG_THREAD_NAME 后，可为每个线程设置可读名称。名称主要用于调试、日志和 shell 中的状态检查；内核不会用它调度线程。

有两种方式可以命名：

  • 静态命名：向 K_THREAD_DEFINE 传入名称；

  • 运行时命名：调用 k_thread_name_set()。这里只保存字符串指针，因此字符串必须在线程整个生命周期内保持有效。

k_thread_name_get() 返回指向名称字符串的指针，k_thread_name_copy() 则把名称复制到调用者提供的缓冲区。在用户模式下，调用线程未必能访问另一个线程名称所在的内存，因此复制方式更安全。

若未启用 CONFIG_THREAD_NAME，k_thread_name_set() 返回错误，k_thread_name_get() 返回 NULL。

线程自省（introspection）

内核提供多个接口，可在运行时查询线程信息。

识别当前线程

k_current_get() 返回当前正在执行的线程标识（k_tid_t）。可将它传给其他线程 API 来操作调用线程自身。

读取线程优先级

k_thread_priority_get() 返回线程当前的调度优先级，包括创建后通过 k_thread_priority_set() 等方式所做的改动。

获取线程状态

k_thread_state_str() 将当前状态的可读描述（如 pending、suspended、ready）写入调用方的缓冲区。此文本用于诊断，请勿在程序中解析它。

遍历全部线程

启用 CONFIG_THREAD_MONITOR 时，k_thread_foreach() 为系统中每个线程调用一次用户提供的回调。遍历期间内部锁会阻止线程创建和终止，因此列表快照一致，但延迟随线程数增长。k_thread_foreach_unlocked() 在每次回调期间释放锁，降低延迟，代价是所见状态不一定严格一致。

查询栈使用量

启用 CONFIG_INIT_STACKS 和 CONFIG_THREAD_STACK_INFO 后，k_thread_stack_space_get() 扫描仍保留初始填充值的区域，计算线程栈尚未使用的字节数。它是构建时栈分析工具及下述运行时栈安全功能的补充。

查询待到期的超时

线程在有时限的操作上阻塞时（如 k_sleep() 或带超时的内核对象操作），便有一个待到期的超时。k_thread_timeout_remaining_ticks() 返回剩余的系统节拍数，k_thread_timeout_expires_ticks() 返回到期时的绝对系统节拍。若没有待到期的超时，两者均返回零。

实现

创建并启动线程

定义栈区及线程控制块，再调用 k_thread_create()，即可创建线程。

可用 K_THREAD_STACK_DEFINE 或 K_KERNEL_STACK_DEFINE 静态分配栈区，以保证它在内存中正确布局。

栈大小参数必须采用以下三种取值之一：

  • 传给 K_THREAD_STACK 或 K_KERNEL_STACK 系列栈实例化宏的原始请求大小；

  • 如果栈对象由 K_THREAD_STACK 系列宏定义，则使用对该对象调用 K_THREAD_STACK_SIZEOF() 得到的值。

  • 如果栈对象由 K_KERNEL_STACK 系列宏定义，则使用对该对象调用 K_KERNEL_STACK_SIZEOF() 得到的值。

也可用 k_thread_stack_alloc() 动态分配栈区，用 k_thread_stack_free() 释放。

创建函数返回线程标识，供后续引用线程。

以下代码创建一个立即开始执行的线程。

#define MY_STACK_SIZE 500
#define MY_PRIORITY 5

extern void my_entry_point(void *, void *, void *);

K_THREAD_STACK_DEFINE(my_stack_area, MY_STACK_SIZE);
struct k_thread my_thread_data;

k_tid_t my_tid = k_thread_create(&my_thread_data, my_stack_area,
                                 K_THREAD_STACK_SIZEOF(my_stack_area),
                                 my_entry_point,
                                 NULL, NULL, NULL,
                                 MY_PRIORITY, 0, K_NO_WAIT);

也可以用 K_THREAD_DEFINE 在编译时声明线程。该宏会自动定义栈区、控制块和线程标识变量。

以下代码与上面的代码片段效果相同。

#define MY_STACK_SIZE 500
#define MY_PRIORITY 5

extern void my_entry_point(void *, void *, void *);

K_THREAD_DEFINE(my_tid, MY_STACK_SIZE,
                my_entry_point, NULL, NULL, NULL,
                MY_PRIORITY, 0, 0);

说明

k_thread_create() 的延迟参数类型为 k_timeout_t，传入 K_NO_WAIT 表示立即启动。K_THREAD_DEFINE 的对应参数则是以毫秒为单位的整数，因此应传 0。

以下代码动态分配线程栈，等待目标线程结束（join），然后释放该栈。

extern void my_entry_point(void *, void *, void *);

k_tid_t my_tid;
void *my_stack_area;

my_stack_area = k_thread_stack_alloc(CONFIG_DYNAMIC_THREAD_STACK_SIZE);
my_tid = k_thread_create(&my_thread_data, my_stack_area,
                          CONFIG_DYNAMIC_THREAD_STACK_SIZE,
                          my_entry_point,
                          NULL, NULL, NULL,
                          MY_PRIORITY, 0, K_NO_WAIT);
k_thread_join(my_tid, K_FOREVER);
k_thread_stack_free(my_stack_area);

用户模式的限制

本节仅适用于已启用 CONFIG_USERSPACE 且用户线程尝试创建新线程的情况。仍然调用 k_thread_create()，但必须满足以下额外约束，否则调用线程将被终止：

  • 调用线程必须已获准访问作为参数传入的子线程对象和栈对象；内核会将二者都作为内核对象跟踪。

  • 子线程及栈对象必须尚未初始化，即线程不在运行且栈内存未被使用。

  • 传入的栈大小不能超过声明时栈对象的边界。

  • 必须使用 K_USER 选项，因为用户线程只能创建其他用户线程。

  • 不得使用 K_ESSENTIAL；用户线程不能标记为关键线程。

  • 子线程的优先级必须有效，且实际优先级不能高于父线程。

降低权限

如果启用 CONFIG_USERSPACE，特权模式线程可用 k_thread_user_mode_enter() 单向切换至用户模式。此操作会重置并清零线程栈，且将线程标记为非关键线程；不可逆转。

终止线程

线程从入口函数返回即可自行终止。

下面展示线程可以如何终止。

void my_entry_point(int unused1, int unused2, int unused3)
{
    while (1) {
        ...
        if (<some condition>) {
            return; /* thread terminates from mid-entry point function */
        }
        ...
    }

    /* thread terminates at end of entry point function */
}

启用 CONFIG_USERSPACE 后，中止线程还会将线程对象和栈对象标记为未初始化，以便复用。

运行时统计

启用 CONFIG_THREAD_RUNTIME_STATS 后，可采集并读取线程的运行时统计信息，例如累计执行周期数。

默认用内核计时器采集统计。部分架构、SoC 或开发板的计时函数可提供更高分辨率的计时器，可通过 CONFIG_THREAD_RUNTIME_STATS_USE_TIMING_FUNCTIONS 启用。

示例如下：

k_thread_runtime_stats_t rt_stats_thread;

k_thread_runtime_stats_get(k_current_get(), &rt_stats_thread);

printk("Cycles: %llu\n", rt_stats_thread.execution_cycles);

k_thread_runtime_stats_all_get() 返回系统所有线程（包括空闲线程）的汇总运行时间，有助于计算整体 CPU 利用率。

启用 CONFIG_SCHED_THREAD_USAGE 后，可用 k_thread_runtime_stats_enable() 和 k_thread_runtime_stats_disable() 在运行时逐线程启停统计，用 k_thread_runtime_stats_is_enabled() 检查某线程是否正在采集。对无需测量的线程关闭采集，可减少每次上下文切换的记账开销。

运行时栈安全检查

启用 CONFIG_THREAD_RUNTIME_STACK_SAFETY 后，内核可在运行时扫描线程栈，判断未使用空间。如果低于该线程配置的阈值，就调用用户定义的处理函数。

此功能面向监控软件。例如，处理函数可记录警告、挂起或中止相应线程，甚至重启系统。它配合构建时栈分析和硬件栈溢出检测，让系统在栈耗尽之前作出反应。

每个线程有一个以字节计的未使用栈空间阈值。检查发现剩余空间低于阈值时，就调用指定的处理函数。零字节（默认值）表示禁用该线程的检查。新线程的默认阈值来自 CONFIG_THREAD_RUNTIME_STACK_SAFETY_DEFAULT_UNUSED_THRESHOLD_PCT，该选项按每个线程总栈大小的百分比指定。

运行时可设置或查询每个线程的阈值：

  • k_thread_runtime_stack_unused_threshold_pct_set() 按总栈大小的百分比（0 至 99）设置阈值。

  • k_thread_runtime_stack_unused_threshold_set() 以字节数设置绝对阈值。

  • k_thread_runtime_stack_unused_threshold_get() 读取当前阈值，单位为字节。

有两个函数执行检查。二者均接收一个指针，用于返回未使用的栈空间量；还接收 k_thread_stack_safety_handler_t 类型的处理函数及用户参数，低于阈值时调用该函数：

  • k_thread_runtime_stack_safety_full_check() 扫描整个栈，精确计算未使用空间。

  • k_thread_runtime_stack_safety_threshold_check() 只进行简化扫描，判断是否已低于阈值。它比完整检查开销小，但得不出精确的剩余空间量。

以下示例设置一个线程，使其未使用空间低于总栈的 10% 时调用处理函数：

void stack_safety_handler(const struct k_thread *thread,
                          size_t unused_space, void *arg)
{
        printk("Thread %p low on stack: %zu bytes unused\n",
               thread, unused_space);
}

/* Trigger the handler once less than 10% of the stack remains unused */
k_thread_runtime_stack_unused_threshold_pct_set(my_tid, 10);

/* Periodically check the thread from a monitoring context */
k_thread_runtime_stack_safety_full_check(my_tid, NULL,
                                         stack_safety_handler, NULL);

建议用法

用线程处理不适合在 ISR 中执行的工作。

将逻辑独立、可并行执行的处理拆分到不同线程中。
