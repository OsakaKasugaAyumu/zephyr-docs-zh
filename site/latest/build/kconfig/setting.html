设置 Kconfig 配置值

非官方简体中文译本 · 英文基线 4.5.99 · C09 · 全站目录（94 篇） · C 批目录 · 本页英文原文

应用开发时可使用 menuconfig 和 guiconfig 交互界面 试验不同配置。本页介绍如何让设置在后续构建中持续生效。

可在Kconfig 搜索页查找全部 Kconfig 选项。

说明

修改 Kconfig 文件之前，建议先阅读Kconfig 技巧与最佳实践。

可见与不可见的 Kconfig 符号

修改配置时，应先区分可见符号和不可见符号。

  • 可见符号在定义时带有提示文字（prompt），会出现在交互配置界面中（因此称为“可见”），也可以在配置文件中设置。

    可见符号示例：

    config FPU
   bool "Support floating point operations"
   depends on HAS_FPU

    在 menuconfig 中，该符号如下所示，可以切换其值：

    [ ] Support floating point operations

  • 不可见符号没有提示文字，不会显示在常规交互配置界面里。用户不能直接控制其值；它的取值来自默认值或其他符号。

    不可见符号示例：

    config CPU_HAS_FPU
   bool
   help
     This symbol is y if the CPU has a hardware floating point unit.

    这里，CPU_HAS_FPU 由其他符号中的 select CPU_HAS_FPU 启用。

在配置文件中设置符号

可在配置文件中设置可见符号。初始配置由板级 *_defconfig 文件和应用设置合并得到；应用设置通常来自 prj.conf。详见下文初始配置。

在配置文件中按以下语法赋值：

CONFIG_<symbol name>=<value>

等号两边不要加空格。

要启用或禁用 bool 符号，请分别赋值 y 或 n。例如，上文的 FPU 可这样启用：

CONFIG_FPU=y

说明

也可以用如下格式的注释，将布尔符号设为 n：

# CONFIG_SOME_OTHER_BOOL is not set

在构建目录的 zephyr/.config 中保存的合并配置就使用这种格式。

接受这种写法有历史原因：Kconfig 配置文件也可以作为 Makefile 解析（Zephyr 未使用这一特性）。将值为 n 的符号表示为未设置的变量，便于在 Make 中判断。

其他类型的符号按如下方式赋值：

CONFIG_SOME_STRING="cool value"
CONFIG_SOME_INT=123

注释以 # 开头：

# This is a comment

只有符号的依赖条件全部满足，配置文件中的赋值才生效；否则会输出警告。要查符号依赖，可使用交互式配置界面（按 / 可直接跳到符号），或在Kconfig 搜索页查找。

初始配置

应用的初始配置由三个来源合并而成：

  1. 特定 BOARD 的配置文件，位于 boards/<VENDOR>/<BOARD>/<BOARD>_defconfig；

  2. 以 CONFIG_ 开头的 CMake 缓存项；

  3. 应用配置。

应用配置可来自以下来源。每个文件都是一个 Kconfig 配置片段，合并后得到此次构建实际使用的配置。默认使用 prj.conf。

  1. 若已设置 CONF_FILE，则合并它指定的文件，作为应用配置。可通过以下途径设置 CONF_FILE：

    1. 在 CMakeLists.txt 中调用 find_package(Zephyr) 之前设置；

    2. 直接或通过 west 传入 -DCONF_FILE=<conf file(s)>；

    3. 从 CMake 变量缓存中读取。

  2. 否则，若应用配置目录内有 boards/<BOARD>.conf，则将它与 prj.conf 合并使用。

  3. 否则，若使用开发板修订版本且应用配置目录内有 boards/<BOARD>_<revision>.conf，则将它与 prj.conf、boards/<BOARD>.conf 合并使用。

  4. 否则，使用应用配置目录中的 prj.conf；若文件不存在，将报告致命错误。

应用还可加入 SoC 专用配置片段。如果 socs/<SOC>_<BOARD_QUALIFIERS>.conf 存在，它会在应用主配置之后、所有板级 Kconfig 片段之前生效。

配置文件默认取自应用配置目录，除非通过 CONF_FILE、EXTRA_CONF_FILE、DTC_OVERLAY_FILE 或 EXTRA_DTC_OVERLAY_FILE 提供绝对路径。在应用的 CMakeLists.txt 中设置上述变量时，可将模块目录变量转义，以 \${ZEPHYR_<module>_MODULE_DIR}/<path-to>/<file> 的形式引用 Zephyr 模块内的文件。

应用配置目录的定义见应用配置目录。

如果 <BOARD>_defconfig 和应用配置对同一符号赋值，应用配置优先。

合并后的配置保存在构建目录的 zephyr/.config 中。

只要 zephyr/.config 已存在且未过期（比所有 BOARD 配置文件和应用配置文件都新），就优先使用它，不重新合并。通过交互式配置界面修改设置时，更改的也是 zephyr/.config。

将 Kconfig 警告视为错误

默认情况下，某些 Kconfig 警告会中止构建，例如对未定义符号赋值；其余可能只打印警告，例如对同一符号重复赋值，或因依赖未满足而忽略赋值。

设置 CMake 变量 KCONFIG_WARNING_AS_ERROR，可将每一条 Kconfig 警告都视为错误：

west build -b <board> <app> -- -DKCONFIG_WARNING_AS_ERROR=y

这在持续集成（CI）中特别有用：配置被悄然忽略往往意味着错误。该变量通过 zephyr_get() 读取，因此也可设置为环境变量，或通过 Zephyr 构建配置 CMake 包 提供。

让一个 Kconfig 符号跟随另一个符号

可以定义一个 Kconfig 符号，让其默认值取自另一个符号。

如果应用或子系统需要自己的配置项，又不想直接依赖公用符号，这种方式会很有用。例如，两者可以独立配置；即使外部设置改名，本地也能保留稳定的名称。

例如，公用配置项为 FOO_STRING，某个子系统希望有一个可单独定制的 SUB_FOO_STRING。

可以这样定义：

config FOO_STRING
        string "Foo"
        default "foo"

config SUB_FOO_STRING
        string "Sub-foo"
        default FOO_STRING

这样，SUB_FOO_STRING 的默认值与 FOO_STRING 相同，但用户仍可分别设置二者。

也可使 SUB_FOO_STRING 不可见，让两个符号保持同步，除非在 defconfig 文件中更改跟随符号的值。

config FOO_STRING
        string "Foo"
        default "foo"

config SUB_FOO_STRING
        string
        default FOO_STRING
        help
          Hidden symbol which follows FOO_STRING
          Can be changed through *.defconfig files.

配置不可见的 Kconfig 符号

调整开发板默认配置时，有时需要设置不可见符号。这应在 boards/<VENDOR>/<BOARD>/Kconfig.defconfig 中完成；它是常规的 Kconfig 文件。

说明

在 .config 文件中对不可见符号赋值不会生效，因此这不仅仅是文件如何组织的问题。

在 Kconfig.defconfig 中赋值，利用的是同一符号可在多处定义的特性。例如，要将下面的 FOO_WIDTH 设为 32：

config FOO_WIDTH
    int

在 Kconfig.defconfig 中补充 FOO_WIDTH 的定义，如下：

if BOARD_MY_BOARD

config FOO_WIDTH
    default 32

endif

说明

符号类型（int）已在首次定义时给出，无需重复。最好只在基础定义中声明一次类型，原因见常用 Kconfig 简写。

Kconfig.defconfig 文件中的 default 优先于符号基础定义里的 default。这是因为系统先包含 Kconfig.defconfig 文件，而 Kconfig 采用第一个满足条件的 default；没有条件就等价于 if y，即始终满足。

外层顶级 if 的条件会传递给符号属性，所以上例的 default 等价于 default 32 if BOARD_MY_BOARD。

在多处定义同一符号

同名符号在多处定义时，各处如同同名的独立定义，属性不会简单追加到前一定义上。只要任意一处定义的条件使符号取得 y，最终值就是 y。因此，重复定义不能让符号的依赖更严格。

例如，只要 DEP1 或 DEP2 为真，下面的 FOO 就满足依赖，而不要求两者都为真：

config FOO
   ...
   depends on DEP1

config FOO
   ...
   depends on DEP2

警告

没有显式依赖的定义也遵循这条规则；不设依赖会使该符号始终可以赋值。在下面的定义中，无论 DEP1 取何值，FOO 默认都会启用。

config FOO
   bool "FOO"
   depends on DEP1

config FOO
   default y

若只想新增默认值而不改变其他行为，可以使用 configdefault 扩展，避免弱化依赖。

说明

修改 Kconfig.defconfig 后，务必用交互式配置界面检查符号的直接依赖。通常需要重申基础定义中的依赖，避免无意中放宽条件。

为什么使用 Kconfig.defconfig

这套机制的一个目的，是避免将 BOARD 固有的设置变成交互界面的可配置项。如果所有板级设置都放在 <BOARD>_defconfig 中，就必须把所有符号设为可见，因为 <BOARD>_defconfig 中的赋值对不可见符号无效。

让用户修改本应固定的设置，会使界面臃肿难懂，也更容易产生无法工作的配置。

遇到板级固定设置，还应考虑是否更适合用设备树（Devicetree）描述。

配置选择项（choice）

配置 Kconfig choice 有两种方法：

  1. 在配置文件中将某一候选符号设为 y。

    把一个候选符号设为 y，其他候选符号会自动变为 n。

    若多个候选都设为 y，只有最后一个赋值为 y 的候选生效，其余变为 n。这样，应用的 prj.conf 可以覆盖板级 defconfig 中的选择。

  2. 在 Kconfig.defconfig 中修改该选择项的 default。

    与普通符号一样，可以在多处定义同一选择项来修改默认值。为此，该选择项必须有名字。

    例如，假定基础定义如下（选择项的名称为 FOO）：

    choice FOO
    bool "Foo choice"
    default B

config A
    bool "A"

config B
    bool "B"

endchoice

    若要把 FOO 的默认选项改为 A，可将以下定义加入 Kconfig.defconfig：

    choice FOO
    default A
endchoice

当选择项的依赖不一定能满足时，应使用 Kconfig.defconfig 方法。这样，当用户满足依赖、让选择项可见时，就会采用指定的默认选择。
