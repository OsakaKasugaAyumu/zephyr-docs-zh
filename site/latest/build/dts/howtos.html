设备树操作指南

非官方简体中文译本 · 英文基线 4.5.99 · C05 · 全站目录（94 篇） · C 批目录 · 本页英文原文

本页按步骤说明如何用设备树完成常见任务。

提示

排查问题请参阅设备树故障排查。

查看最终设备树和生成的头文件

开发板设备树（BOARD.dts）用 #include 预处理指令引入共用节点定义，至少包括 SoC 的 .dtsi。逐个打开这些文件（例如 dts/<ARCH>/<vendor>/<soc>.dtsi）也能弄清设备树的内容，但比较耗时。

如果只想查看板上最终使用的设备树，先构建一个应用，再打开构建目录里的 zephyr.dts。

提示

要查看不含任何应用覆盖文件修改的基础设备树，可以构建 Hello World。

例如，为 面向 Arm Cortex-M3 的 QEMU 仿真板 构建 Hello World：

# --cmake-only here just forces CMake to run, skipping the
# build process to save time.
west build -b qemu_cortex_m3 samples/hello_world --cmake-only

将 qemu_cortex_m3 替换为自己的开发板目标即可。

CMake 将打印输入和输出文件的位置，例如：

-- Found BOARD.dts: .../zephyr/boards/arm/qemu_cortex_m3/qemu_cortex_m3.dts
-- Generated zephyr.dts: .../zephyr/build/zephyr/zephyr.dts
-- Generated devicetree_generated.h: .../zephyr/build/zephyr/include/generated/zephyr/devicetree_generated.h

zephyr.dts 是 DTS 格式的最终设备树。

devicetree_generated.h 是对应的自动生成头文件。

有关这些文件的详细信息，见输入与输出文件。

从设备树节点获取 struct device

编写 Zephyr 应用时，经常需要从设备树节点取得驱动层对应的 struct device。

例如，在以下设备树片段中，你可能需要取得 serial@40002000 对应的 struct device：

/ {
        soc {
                serial0: serial@40002000 {
                        status = "okay";
                        current-speed = <115200>;
                        /* ... */
                };
        };

        aliases {
                my-serial = &serial0;
        };

        chosen {
                zephyr,console = &serial0;
        };
};

先为所需设备取得节点标识符。有多种方法，可根据应用需要选择。下面是一些例子：

/* Option 1: by node label */
#define MY_SERIAL DT_NODELABEL(serial0)

/* Option 2: by alias */
#define MY_SERIAL DT_ALIAS(my_serial)

/* Option 3: by chosen node */
#define MY_SERIAL DT_CHOSEN(zephyr_console)

/* Option 4: by path */
#define MY_SERIAL DT_PATH(soc, serial_40002000)

拿到节点标识符后，有两种方式可以继续。第一种是使用 DEVICE_DT_GET 取得设备：

const struct device *const uart_dev = DEVICE_DT_GET(MY_SERIAL);

if (!device_is_ready(uart_dev)) {
        /* Not ready, do not use */
        return -ENODEV;
}

DEVICE_DT_GET 还有 DEVICE_DT_GET_OR_NULL、DEVICE_DT_GET_ONE 和 DEVICE_DT_GET_ANY 等变体。这种写法在构建时取得指针，没有运行时开销，适合把设备指针存为配置数据。但设备可能尚未初始化或初始化失败，因此将指针传给任何 API 之前，必须检查设备是否就绪。（device_get_binding() 已代为检查。）

如果到运行时才能确定设备（例如在 shell 应用中由用户选择），可以将 device_get_binding() 与设备名配合使用来取得 struct device：

const char *dev_name = /* TODO: insert device name from user */;
const struct device *uart_dev = device_get_binding(dev_name);

随后即可将 uart_dev 传给 通用异步收发器（UART） API，例如 uart_configure()。其他设备类型也可使用类似写法，但要调用该类设备对应的 API。

遇到问题时见设备树故障排查。先检查节点是否设为 status = "okay"，例如：

#define MY_SERIAL DT_NODELABEL(my_serial)

#if DT_NODE_HAS_STATUS(MY_SERIAL, okay)
const struct device *const uart_dev = DEVICE_DT_GET(MY_SERIAL);
#else
#error "Node is disabled"
#endif

若出现 #error，请确认已在设备树中启用节点。有时代码能编译，却会在链接时报出类似错误：

...undefined reference to `__device_dts_ord_N'
collect2: error: ld returned 1 exit status

这通常意味着驱动因 Kconfig 配置而未参与编译，产生了找不到定义的引用。如果顺利编译，最后还需检查设备是否就绪：

if (!device_is_ready(uart_dev)) {
     printk("Device not ready\n");
}

如果设备未就绪，很可能是初始化函数执行失败。可启用日志或调试驱动代码。也可以在运行时用 device_get_binding() 取得设备引用；若返回 NULL，可能是驱动初始化失败，也可能是设备不存在。

查找设备树绑定

设备树绑定（bindings）是 YAML 文件，它声明了节点支持哪些内容。因此要正确使用节点，首先得找到它的绑定。

如果尚未取得这些文件，请先查看最终设备树和生成的头文件。打开生成的头文件，开头的块注释会列出节点：

/*
 * [...]
 * Nodes in dependency order (ordinal and path):
 *   0   /
 *   1   /aliases
 *   2   /chosen
 *   3   /flash@0
 *   4   /memory@20000000
 *          (etc.)
 * [...]
 */

记下目标节点的路径（如 /flash@0），在文件内搜索该路径。如果节点匹配到绑定，相应输出的开头类似下例：

/*
 * Devicetree node:
 *   /flash@0
 *
 * Binding (compatible = soc-nv-flash):
 *   $ZEPHYR_BASE/dts/bindings/mtd/soc-nv-flash.yaml
 * [...]
 */

排查方法见检查是否缺少绑定。

设置设备树覆盖文件

设备树覆盖文件的概念见设备树入门（Introduction to devicetree）。CMake 变量 DTC_OVERLAY_FILE 是覆盖文件列表，条目以空格或分号分隔。如果 DTC_OVERLAY_FILE 列出多个文件，C 预处理器会依次引入。指定 Zephyr 模块中的文件时，可像 \${ZEPHYR_<module>_MODULE_DIR}/<path-to>/dts.overlay 这样转义模块目录变量。

可以用 DTC_OVERLAY_FILE 精确指定要使用的文件。下面是使用 west build 的一个示例。

如果没有设置 DTC_OVERLAY_FILE，构建系统会依次在应用配置目录中查找覆盖文件：

  1. 若存在 socs/<SOC>_<BOARD_QUALIFIERS>.overlay，则使用该文件。

  2. 若还存在 boards/<BOARD>.overlay，则追加使用该文件。

  3. 如果开发板有多个修订版本且存在 boards/<BOARD>_<revision>.overlay，则也追加使用该文件。

  4. 如果上述步骤找到至少一个文件，查找就此结束，只使用已找到的文件。

  5. 否则，若存在 <BOARD>.overlay，则使用它并停止查找。

  6. 若以上均未找到，且 app.overlay 存在，则使用它。

可用 EXTRA_DTC_OVERLAY_FILE 指定额外的覆盖文件，同时保留上述自动查找机制。

构建系统将 EXTRA_DTC_OVERLAY_FILE 中的文件追加到 DTC_OVERLAY_FILE 之后。因此 EXTRA_DTC_OVERLAY_FILE 所作的修改优先于 DTC_OVERLAY_FILE。

除非通过 DTC_OVERLAY_FILE 或 EXTRA_DTC_OVERLAY_FILE 提供绝对路径，否则都从应用配置目录获取配置文件。

应用配置目录的定义见应用配置目录。

使用Shields也会增加设备树覆盖文件。

DTC_OVERLAY_FILE 的值保存在 CMake 缓存中，供后续构建继续使用。

构建系统（build system）会在配置阶段打印找到的全部设备树覆盖文件，例如：

-- Found devicetree overlay: .../some/file.overlay

使用设备树覆盖文件（overlay）

将覆盖文件加入构建的方法见设置设备树覆盖文件。

可以用多种方式覆盖节点属性值。例如，若 BOARD.dts 中包含以下节点：

/ {
        soc {
                serial0: serial@40002000 {
                        status = "okay";
                        current-speed = <115200>;
                        /* ... */
                };
        };
};

下面几种写法等价，都能在覆盖文件中修改 current-speed：

/* Option 1 */
&serial0 {
     current-speed = <9600>;
};

/* Option 2 */
&{/soc/serial@40002000} {
     current-speed = <9600>;
};

后续示例统一采用 &serial0 写法。

也可以通过覆盖文件添加别名：别名就是 /aliases 节点的一个属性。例如：

/ {
     aliases {
             my-serial = &serial0;
     };
};

选定节点的用法相同。例如：

/ {
     chosen {
             zephyr,console = &serial0;
     };
};

要删除一个属性，可使用以下写法。如果 BOARD.dts 中的布尔属性为真，要将它置为假，同样应删除该属性：

&serial0 {
     /delete-property/ some-unwanted-property;
};

覆盖文件还可添加子节点。例如，可在已有 SPI 或 I2C 总线节点下添加设备：

/* SPI device example */
&spi1 {
     my_spi_device: temp-sensor@0 {
             compatible = "...";
             label = "TEMP_SENSOR_0";
             /* reg is the chip select number, if needed;
              * If present, it must match the node's unit address. */
             reg = <0>;

             /* Configure other SPI device properties as needed.
              * Find your device's DT binding for details. */
             spi-max-frequency = <DT_FREQ_M(4)>;
     };
};

/* I2C device example */
&i2c2 {
     my_i2c_device: touchscreen@76 {
             compatible = "...";
             label = "TOUCHSCREEN";
             /* reg is the I2C device address.
              * It must match the node's unit address. */
             reg = <76>;

             /* Configure other I2C device properties as needed.
              * Find your device's DT binding for details. */
     };
};

其他总线设备也可按类似步骤配置：

  • 在父总线下创建设备子节点；

  • 按绑定设置其属性。

假定 my_spi_device 和 my_i2c_device 这两个 compatible 值都有相应驱动，就可以通过 Kconfig 启用驱动，为新加的总线设备节点获取 struct device，并通过相应驱动 API 使用它。

使用设备树 API 编写设备驱动

支持设备树的设备驱动程序应为每个已启用（status = "okay"）且具有驱动所支持的 compatible（或一组相关 compatible 值）的设备树节点创建一个 struct device。

首先为驱动支持的设备定义设备树绑定（devicetree binding）。可从类似驱动的现有绑定入手。最小的绑定只需如下内容：

description: <Human-readable description of your binding>
compatible: "foo-company,bar-device"
include: base.yaml

查找现有绑定的方法见查找设备树绑定。

有了绑定后，驱动的 C 文件即可通过设备树 API 找出具有目标 compatible 且 status = "okay" 的节点，并为每个节点实例化一个 struct device。创建 struct device 有两种方式：使用实例编号，或使用节点标签。

无论选择哪种方式：

  • 每个 struct device 的名称应设为对应节点的 label 属性，方便驱动使用者按通常方式从设备树节点获取 struct device。

  • 只要可行，设备初始配置就应取自设备树属性，以便用户通过设备树覆盖文件配置驱动。

下面的例子假定你已经实现设备专用的配置结构、运行数据结构和 API 函数，例如：

/* my_driver.c */
#include <zephyr/drivers/some_api.h>

/* Define data (RAM) and configuration (ROM) structures: */
struct my_dev_data {
     /* per-device values to store in RAM */
};
struct my_dev_cfg {
     uint32_t freq; /* Just an example: initial clock frequency in Hz */
     /* other configuration to store in ROM */
};

/* Implement driver API functions (drivers/some_api.h callbacks): */
static int my_driver_api_func1(const struct device *dev, uint32_t *foo) { /* ... */ }
static int my_driver_api_func2(const struct device *dev, uint64_t bar) { /* ... */ }
static struct some_api my_api_funcs = {
     .func1 = my_driver_api_func1,
     .func2 = my_driver_api_func2,
};

方式一：使用实例编号创建设备

尽可能选择此方式，使用基于实例的 API。但前提是驱动对应 compatible 的所有节点都可以同等对待，无需区分特定实例。

先将 DT_DRV_COMPAT 定义为驱动所支持的 compatible 值的小写加下划线形式。例如设备树中为 "vnd,my-device"，则驱动 C 文件中应将 DT_DRV_COMPAT 定义为 vnd_my_device：

/*
 * Put this near the top of the file. After the includes is a good place.
 * (Note that you can therefore run "git grep DT_DRV_COMPAT drivers" in
 * the zephyr Git repository to look for example drivers using this style).
 */
#define DT_DRV_COMPAT vnd_my_device

重要

如上所示，DT_DRV_COMPAT 不含引号或特殊字符。从 compatible 属性生成 DT_DRV_COMPAT 时，去掉引号，将特殊字符替换为下划线。

在定义 my_api_funcs 后，定义一个实例化宏，通过实例编号创建每个 struct device。

/*
 * This instantiation macro is named "CREATE_MY_DEVICE".
 * Its "inst" argument is an arbitrary instance number.
 *
 * Put this near the end of the file, e.g. after defining "my_api_funcs".
 */
#define CREATE_MY_DEVICE(inst)                                       \
     static struct my_dev_data my_data_##inst = {                    \
             /* initialize RAM values as needed, e.g.: */            \
             .freq = DT_INST_PROP(inst, clock_frequency),            \
     };                                                              \
     static const struct my_dev_cfg my_cfg_##inst = {                \
             /* initialize ROM values as needed. */                  \
     };                                                              \
     DEVICE_DT_INST_DEFINE(inst,                                     \
                           my_dev_init_function,                     \
                           NULL,                                     \
                           &my_data_##inst,                          \
                           &my_cfg_##inst,                           \
                           MY_DEV_INIT_LEVEL, MY_DEV_INIT_PRIORITY,  \
                           &my_api_funcs);

注意这里如何用 DT_INST_PROP、DEVICE_DT_INST_DEFINE 等 API 读取节点数据。它们读取由 DT_DRV_COMPAT 指定 compatible 的节点中编号为 inst 的实例。

最后，将实例化宏传给 DT_INST_FOREACH_STATUS_OKAY：

/* Call the device creation macro for each instance: */
DT_INST_FOREACH_STATUS_OKAY(CREATE_MY_DEVICE)

DT_INST_FOREACH_STATUS_OKAY 展开后，会针对每一个已启用且匹配 DT_DRV_COMPAT 的节点调用一次 CREATE_MY_DEVICE。它不会给 CREATE_MY_DEVICE 的展开结果追加分号。因此，要支持多个设备，该宏必须展开为以分号结尾的语句或函数定义。

方式二：使用节点标签创建设备

有些驱动不能使用实例编号。例如，SoC 外设驱动可能依赖厂商针对不同 IP 块提供的 HAL API 来实现 Zephyr 回调。这种情况应使用 DT_NODELABEL 指向具体外设节点，再通过 devicetree.h 的通用 API读取节点数据。

要让此方式生效，SoC 的 dtsi 文件必须为驱动支持的各 IP 块提供恰当的标签，如 mydevice0、mydevice1。设备树通常如下：

/ {
        soc {
                mydevice0: dev@0 {
                        compatible = "vnd,my-device";
                };
                mydevice1: dev@1 {
                        compatible = "vnd,my-device";
                };
        };
};

驱动可用设备树中的 mydevice0、mydevice1 标签操作对应节点：

/*
 * This is a convenience macro for creating a node identifier for
 * the relevant devices. An example use is MYDEV(0) to refer to
 * the node with label "mydevice0".
 */
#define MYDEV(idx) DT_NODELABEL(mydevice ## idx)

/*
 * Define your instantiation macro; "idx" is a number like 0 for mydevice0
 * or 1 for mydevice1. It uses MYDEV() to create the node label from the
 * index.
 */
#define CREATE_MY_DEVICE(idx)                                        \
     static struct my_dev_data my_data_##idx = {                     \
             /* initialize RAM values as needed, e.g.: */            \
             .freq = DT_PROP(MYDEV(idx), clock_frequency),           \
     };                                                              \
     static const struct my_dev_cfg my_cfg_##idx = { /* ... */ };    \
     DEVICE_DT_DEFINE(MYDEV(idx),                                    \
                     my_dev_init_function,                           \
                     NULL,                                           \
                     &my_data_##idx,                                 \
                     &my_cfg_##idx,                                  \
                     MY_DEV_INIT_LEVEL, MY_DEV_INIT_PRIORITY,        \
                     &my_api_funcs)

注意这里如何用 DT_PROP 和 DEVICE_DT_DEFINE 等 API 访问节点数据。

最后，逐一检查节点是否启用，并用 CREATE_MY_DEVICE 实例化各个 struct device：

#if DT_NODE_HAS_STATUS(DT_NODELABEL(mydevice0), okay)
CREATE_MY_DEVICE(0)
#endif

#if DT_NODE_HAS_STATUS(DT_NODELABEL(mydevice1), okay)
CREATE_MY_DEVICE(1)
#endif

由于此方式不使用 DT_INST_FOREACH_STATUS_OKAY()，驱动作者必须自行遍历所有可能节点并调用 CREATE_MY_DEVICE()，例如根据所支持 SoC 的外设列表逐个处理。

依赖其他设备的驱动

有时一个 struct device 依赖另一个 struct device，需要取得指向它的指针。例如，传感器可能需要其 SPI 总线控制器的设备指针。建议如下：

  • 设计绑定时，尽量使它能使用 devicetree.h 中的硬件专用 API。

  • 对于总线上的设备，驱动绑定应包含 dts/bindings/spi/spi-device.yaml 之类的文件，继承该总线可寻址设备的公用定义。之后可用 DT_BUS 等 API 取得总线节点标识符，再按通常方式为总线从设备树节点获取 struct device。

可在现有绑定和设备驱动中查找示例。

依赖特定开发板设备的应用

要使同一应用不改代码就能在不同开发板上运行，一种方法是用设备树别名指向各板实际的硬件，Blinky：LED 闪烁 示例即是如此。应用可通过 BOARD.dts 或设备树覆盖文件选择设备。
