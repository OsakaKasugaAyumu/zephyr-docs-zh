应用开发（Application Development）

非官方简体中文译本 · 英文基线 4.5.99 · B03 · 全站目录（79 篇） · B 批目录 · 本页英文原文

说明

本文使用以下路径作为示例：

  • 应用目录（<app>）类似于 <home>/zephyrproject/app

  • 对应的构建目录为 <app>/build

下文将解释这些术语。在 Linux/macOS 上，<home> 相当于 ~；在 Windows 上，它是 %userprofile%。

将应用放在工作区（<home>/zephyrproject）内，更方便运行 west build 等命令。不过，只要正确设置 ZEPHYR_BASE，应用可以放在任意位置。

概述

Zephyr 的构建系统以 CMake 为基础。

构建流程以应用为入口：由应用发起 Zephyr 源码的构建，同时控制自身及 Zephyr 的配置与构建，最终将二者编译、链接为一个二进制文件。

zephyr 主仓库包含 Zephyr 源码、配置文件和构建系统。其旁边通常还安装了若干模块（外部项目），用来集成第三方源码。

应用目录中的文件把应用与 Zephyr 及所需模块连接起来。所有应用专用的配置文件和源码都放在这里。

一个简单的 Zephyr 应用包含以下文件：

<app>
├── CMakeLists.txt
├── app.overlay
├── prj.conf
├── VERSION
└── src
    └── main.c

各文件的用途如下：

  • CMakeLists.txt：告诉构建系统到哪里查找应用的其他文件，并将应用目录接入 Zephyr 的 CMake 构建系统。这样就能使用板级配置文件，在真实硬件或仿真环境中运行、调试生成的程序，以及使用其他构建功能。

  • app.overlay：设备树覆盖文件（devicetree overlay）。它对各目标板的基础设备树施加本应用所需的修改，通常用来配置应用使用的硬件。

    构建系统默认查找 app.overlay。可以另加覆盖文件；系统也会查找其他默认文件。

    设备树的详细说明见设备树（Devicetree）。

  • prj.conf：Kconfig 配置片段，为一个或多个配置项指定应用所需的值。构建时，这些值与其他设置合并为最终配置。Kconfig 片段通常配置应用使用的软件功能。

    构建系统默认查找 prj.conf。可以另加 Kconfig 片段；系统也会查找其他默认文件。

    详见下文的Kconfig 配置。

  • VERSION：包含若干版本信息字段的文本文件，可用于管理应用的生命周期，并在签署应用镜像时自动提供应用版本。

    关于此文件和用法，见应用版本管理。

  • main.c：源文件。应用通常使用 C、C++ 或汇编语言编写。Zephyr 的惯例是在 <app> 下建立 src 子目录来存放源码。

定义好应用后，用 CMake 生成构建目录；其中的构建文件用于编译应用和 Zephyr，并将两者链接成可在板上运行的二进制文件。最简单的方式是运行 west build，也可以直接调用 CMake。产物始终放在单独的构建目录中：Zephyr 不支持在源码树内原地构建。

以下各节先说明如何创建、构建和运行 Zephyr 应用，随后给出更详细的参考资料。

应用类型

按 <app> 的位置，Zephyr 应用分为三类：

应用类型

<app> 的位置

仓库

zephyr 仓库内

工作区（workspace）

安装了 Zephyr 的 west 工作区内

独立应用

其他位置

下文将分别介绍。构建系统如何支持这些类型，见 Zephyr CMake 包。

Zephyr 仓库内应用

位于 Zephyr west 工作区 的 zephyr 源码仓库内的应用称为 Zephyr 仓库内应用。下例中的hello_world 示例即属此类：

zephyrproject/
├─── .west/
│    └─── config
└─── zephyr/
     ├── arch/
     ├── boards/
     ├── cmake/
     ├── samples/
     │    ├── hello_world/
     │    └── ...
     ├── tests/
     └── ...

Zephyr 工作区应用

位于工作区（workspace）内、但在 zephyr 仓库以外的应用称为 Zephyr 工作区应用。下例中的 app 即属此类：

zephyrproject/
├─── .west/
│    └─── config
├─── zephyr/
├─── bootloader/
├─── modules/
├─── tools/
├─── <vendor/private-repositories>/
└─── applications/
     └── app/

独立应用（freestanding application）

位于 Zephyr 工作区（workspace）以外的 Zephyr 应用称为独立应用。下例中的 app 即属此类：

<home>/
├─── zephyrproject/
│     ├─── .west/
│     │    └─── config
│     ├── zephyr/
│     ├── bootloader/
│     ├── modules/
│     └── ...
│
└─── app/
     ├── CMakeLists.txt
     ├── prj.conf
     └── src/
         └── main.c

创建应用

既可以从工作区参考应用开始，也可以手动创建应用。

使用工作区参考应用

Git 仓库 example-application 提供了一个参考工作区应用。按下文创建自己的应用时，建议以它为参考。

example-application 展示了多项常用功能，例如：

  • 自定义板级移植

  • 自定义设备树绑定

  • 自定义设备驱动程序

  • 持续集成（CI）配置，包括使用 twister

  • 自定义 west 扩展命令

example-application 基本用法

在现有 Zephyr 工作区内使用 example-application，最简单的是按以下步骤操作：

cd <home>/zephyrproject
git clone https://github.com/zephyrproject-rtos/example-application my-app

上述目录名 my-app 可自行更改。进入该目录后，按需要调整内容。由于使用的是现有 Zephyr 工作区，可以使用 west build 等 west 命令进行构建、烧写和调试。

example-application 进阶用法

也可用 example-application 仓库作为起点，构建自己的 Zephyr 软件发行版。例如，可以：

  • 移除不需要的 Zephyr 模块；

  • 添加自己的其他仓库；

  • 用自己的版本替换 Zephyr 提供的仓库；

  • 与他人分享成果并继续协作。

example-application 中包含 west.yml，因此本身也是 west 的清单仓库（manifest repository）。按以下步骤创建定制工作区：

cd <home>
mkdir my-workspace
cd my-workspace
git clone https://github.com/zephyrproject-rtos/example-application my-manifest-repo
west init -l my-manifest-repo

这样会创建采用T2 拓扑的新工作区，以 my-manifest-repo 为清单仓库。my-workspace 和 my-manifest-repo 两个名字都可以更改。

接下来定制清单仓库。克隆时其内容与 example-application 相同；之后可编辑 my-manifest-repo/west.yml，按需调整仓库集合。如何向工作区添加或移除仓库，见清单导入（manifest imports）中的示例。其他文件也可按需修改。

调整完毕后运行：

west update

工作区即可使用。

将修改后的 my-manifest-repo 推送到远端，即可分享成果。例如，推送到 https://git.example.com/my-manifest-repo 后，其他人运行以下命令即可建立相同的工作区：

west init -m https://git.example.com/my-manifest-repo my-workspace
cd my-workspace
west update

此后，各方可向所用仓库推送更改并协作开发；按需更新 my-manifest-repo/west.yml，增删仓库或更改所用内容。

手动创建应用

以下步骤可从零创建基本应用目录。不过，以 example-application 或 Zephyr 的某个示例与演示为起点通常更简单。

  1. 创建应用目录。

    例如，在 Unix shell 或 Windows 的 cmd.exe 提示符下执行：

    mkdir app

    警告

    Zephyr 不支持在路径含空格的目录中构建或创建应用。因此 Windows 路径 C:\Users\YourName\app 可以使用，C:\Users\Your Name\app 则不行。

  2. 创建源文件。

    建议将所有应用源码放入名为 src 的子目录，便于与工程文件区分。

    延续前例，输入：

    cd app
mkdir src

  3. 将应用源码放入 src 子目录。此例假定已创建 src/main.c。

  4. 在 app 目录中创建 CMakeLists.txt，内容如下：

    cmake_minimum_required(VERSION 3.28.0)

find_package(Zephyr)
project(my_zephyr_app)

target_sources(app PRIVATE src/main.c)

    说明：

    • CMake 要求调用 cmake_minimum_required()，下一行引入的 Zephyr 包也会调用它。如果本机 CMake 版本低于 CMakeLists.txt 或 Zephyr 包中指定的任一最低版本，就会报错。

    • find_package(Zephyr) 引入 Zephyr 构建系统，并创建名为 app 的 CMake 目标（见 Zephyr CMake 包）。将源文件加入该目标即可参与构建。Zephyr 包将 Zephyr-Kernel 定义为 CMake 工程，并启用 C、CXX 和 ASM 语言支持。

    • project(my_zephyr_app) 定义应用自身的 CMake 工程。必须放在 find_package(Zephyr) 之后，避免干扰 Zephyr 的 project(Zephyr-Kernel)。

    • target_sources(app PRIVATE src/main.c) 将源文件加入 app 目标，必须放在定义该目标的 find_package(Zephyr) 之后。可使用 target_sources() 添加任意数量的源文件。

  5. 至少创建一个 Kconfig 片段（通常为 prj.conf），在其中设置应用需要的配置值。见Kconfig 配置。即使没有任何配置项要设置，也应创建一个空文件。

  6. 配置应用所需的设备树覆盖文件，通常名为 app.overlay。见设置设备树覆盖文件。

  7. 按需添加其他文件，例如 twister 配置、持续集成文件、文档等。

重要构建变量

Zephyr 构建系统支持许多控制变量。本节介绍每位开发者都应了解的几个关键变量。

说明

向构建系统传递 BOARD、CONF_FILE 和 DTC_OVERLAY_FILE 有三种方式，按优先级从高到低排列如下：

  • 调用 west build 或 cmake 时，通过命令行选项 -D 传入。指定多个覆盖文件时应加引号，例如 "file1.overlay;file2.overlay"。

  • 设为环境变量。

  • 在 CMakeLists.txt 中使用 set(<VARIABLE> <VALUE>) 语句。

  • ZEPHYR_BASE：构建系统使用的 Zephyr 基目录。find_package(Zephyr) 会自动将其设为 CMake 缓存变量；也可设置同名环境变量 ZEPHYR_BASE，强制 CMake 使用指定的 Zephyr 安装。

  • BOARD：选择应用构建所用的开发板及其默认配置。内置开发板见支持的开发板与扩展板；添加板卡支持见开发板移植指南。

  • CONF_FILE：指定一个或多个 Kconfig 配置片段文件，多个文件名用空格或分号分隔。文件中的设置会覆盖相应默认值。

    详见初始配置。

  • EXTRA_CONF_FILE：额外的 Kconfig 配置片段，多个文件名用空格或分号分隔。可保留 CONF_FILE 的默认值，同时叠加额外的配置。

  • DTC_OVERLAY_FILE：指定一个或多个设备树覆盖文件，多个文件名以分号分隔。示例见设置设备树覆盖文件；设备树与 Zephyr 的关系见设备树入门。

  • EXTRA_DTC_OVERLAY_FILE：要额外使用的设备树覆盖文件，多个文件名以分号分隔。可保留 DTC_OVERLAY_FILE 的默认值，同时叠加其他覆盖文件。

  • SHIELD：见Shields。

  • ZEPHYR_MODULES：一个CMake 列表，列出包含额外源码、Kconfig 等内容的目录绝对路径。详见模块（外部项目）。如设置此变量，就必须列出要使用的全部模块；构建系统不会再从 west 自动收集模块。

  • EXTRA_ZEPHYR_MODULES：类似 ZEPHYR_MODULES，但会追加到 west 找到的模块列表，而非将其替换。

  • FILE_SUFFIX：Kconfig 片段与设备树覆盖文件可选的文件名后缀。有带后缀的文件时使用它；否则回退到原文件名。详见文件后缀。

  • KCONFIG_WARNING_AS_ERROR：把所有 Kconfig 警告视为错误，包括默认只打印的警告。详见将 Kconfig 警告视为错误。

说明

可通过Zephyr 构建配置 CMake 包共享这些变量的通用设置。

应用的 CMakeLists.txt

每个应用都必须有 CMakeLists.txt。它是构建系统的顶层入口。生成的 zephyr.elf 镜像包含应用和内核库。

以下介绍可在 CMakeLists.txt 中进行的设置。请按顺序操作。

  1. 如果只针对一块板构建，可另起一行指定该板的配置名。例如：

    set(BOARD qemu_x86)

    可用开发板见支持的开发板与扩展板。

    构建系统按以下顺序确定 BOARD 的值；找到有效的 BOARD 值后，CMake 不再继续向下查找：

    • CMake 缓存中先前使用的值优先级最高，防止用不同于配置阶段的 BOARD 值进行构建。

    • 其次使用 CMake 命令行上通过 -DBOARD=YOUR_BOARD 设置的值，可直接传入，也可经由 west build 传入。

    • 接着，若已设置 环境变量 BOARD，则使用它的值。

    • 最后，若按本步骤在应用的 CMakeLists.txt 中设置了 BOARD，则使用该值。

  2. 如果不用常规的 prj.conf，请将 CONF_FILE 设为实际使用的一个或多个配置文件；多个文件名用单个空格或分号分隔。若不想在一处设置 CONF_FILE，可用 CMake 列表逐步组合各配置片段。例如：

    set(CONF_FILE "fragment_file1.conf")
list(APPEND CONF_FILE "fragment_file2.conf")

    详见初始配置。

  3. 使用设备树覆盖文件时，可能需要设置 DTC_OVERLAY_FILE。见设置设备树覆盖文件。

  4. 如果应用自定义了内核配置选项，请在应用的 CMakeLists.txt 旁创建 Kconfig 文件。

    Kconfig 的详细说明见手册的 Kconfig 章节。

    一种不太常见的高级用法，是让应用定义自己的配置选项，针对不同的构建配置给它们赋不同的值。

    如果只是要给 Zephyr 已有的配置项指定应用专用的值，请参阅上文关于 CONF_FILE 的说明。

    可按以下方式组织 Kconfig：

    # SPDX-License-Identifier: Apache-2.0

mainmenu "Your Application Name"

# Your application configuration options go here

# Sources Kconfig.zephyr in the Zephyr root directory.
#
# Note: All 'source' statements work relative to the Zephyr root directory (due
# to the $srctree environment variable being set to $ZEPHYR_BASE). If you want
# to 'source' relative to the current Kconfig file instead, use 'rsource' (or a
# path relative to the Zephyr root).
source "Kconfig.zephyr"

    说明

    source 语句会直接展开环境变量，无需定义 option env="ZEPHYR_BASE" 这种用于中转的 Kconfig 符号。如果使用此类符号，它必须与环境变量同名。

    详见Kconfig 扩展。

    构建系统会自动检测应用目录中的 Kconfig。也可将 CMake 变量 KCONFIG_ROOT 设为绝对路径，从其他位置加载该文件。

  5. 另起一行声明应用需要 Zephyr，位置应在前面各步骤添加的语句之后：

    find_package(Zephyr)
project(my_zephyr_app)

    说明

    若要允许显式设置环境变量 ZEPHYR_BASE 来指定 Zephyr 安装，可使用 find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})。Zephyr 的所有示例都支持环境变量 ZEPHYR_BASE。

  6. 把应用的各个源文件添加到目标库 app，每个文件一行，如下：

    target_sources(app PRIVATE src/main.c)

下面是一个简单的 CMakeList.txt 示例：

set(BOARD qemu_x86)

find_package(Zephyr)
project(my_zephyr_app)

target_sources(app PRIVATE src/main.c)

CMake 属性 HEX_FILES_TO_MERGE 利用 Kconfig 和 CMake 提供的应用配置，将外部构建的 hex 文件与 Zephyr 应用生成的 hex 文件合并。例如：

set_property(GLOBAL APPEND PROPERTY HEX_FILES_TO_MERGE
    ${app_bootloader_hex}
    ${PROJECT_BINARY_DIR}/${KERNEL_HEX_NAME}
    ${app_provision_hex})

CMakeCache.txt

CMake 用 CMakeCache.txt 持久保存键值字符串，在各次运行间复用编译和构建选项、依赖库路径等信息。在空的构建目录中首次运行 CMake 时会创建此文件。

更多说明见 CMake 官方的CMake 缓存文档。

应用配置

Zephyr 从应用配置目录读取配置文件，但前述参数明确指定了绝对路径时例外，例如 CONF_FILE、EXTRA_CONF_FILE、DTC_OVERLAY_FILE 和 EXTRA_DTC_OVERLAY_FILE。

说明

Kconfig 片段扩展名为 .conf，设备树覆盖文件扩展名为 .overlay。不要给 Kconfig 片段加 overlay 前缀：该术语专用于设备树，混用会造成歧义。

应用配置目录

应用配置目录由变量 APPLICATION_CONFIG_DIR 指定。

APPLICATION_CONFIG_DIR 的来源按优先级从高到低排列如下：

  1. 如果用户通过 -DAPPLICATION_CONFIG_DIR=<path> 指定了 APPLICATION_CONFIG_DIR，或在 CMake 文件中于 find_package(Zephyr) 之前设置它，就以此目录作为应用配置目录。

  2. 否则，使用应用的源码目录。

Kconfig 配置

应用配置通常放在应用目录的 prj.conf 中。例如，以下赋值启用 C++ 支持：

CONFIG_CPP=y

从已有示例入手是个好方法。

设置 Kconfig 值的详细说明见设置 Kconfig 配置值。同页的初始配置介绍初始配置的来源；完整配置项列表见Kconfig 搜索，涉及安全性的说明见安全加固工具。

手册的 Kconfig 章节中的其他页面也值得阅读，尤其是在准备添加新配置项时。

实验性功能

Zephyr 持续演进，部分功能仍处在开发早期。这些功能会在 Kconfig 标题中标记为 [EXPERIMENTAL]。

可设置 CONFIG_WARN_EXPERIMENTAL，使 CMake 在配置阶段发现启用的实验性功能时给出警告。

CONFIG_WARN_EXPERIMENTAL=y

例如，如果 CONFIG_FOO 是实验性选项，同时启用它和 CONFIG_WARN_EXPERIMENTAL，构建应用时就会在 CMake 配置阶段看到以下警告：

warning: Experimental symbol FOO is enabled.

设备树覆盖文件

参见设置设备树覆盖文件。

文件后缀

同一套应用源码可能用于多个产品或构建变体，各变体需要不同的 Kconfig 和设备树设置。配置应用时，FILE_SUFFIX 可自动将后缀加入 Kconfig 片段和板级覆盖文件的文件名。如果带后缀的文件不存在，则回退到不带后缀的文件。

假设项目的目录结构如下：

<app>
├── CMakeLists.txt
├── prj.conf
├── prj_mouse.conf
├── boards
│   ├── native_sim.overlay
│   └── qemu_cortex_m3_mouse.overlay
└── src
    └── main.c

  • 不定义 FILE_SUFFIX，为 native_sim 正常构建时，使用 prj.conf 和 boards/native_sim.overlay。

  • 不定义 FILE_SUFFIX，为 qemu_cortex_m3 正常构建时，使用 prj.conf，不使用应用设备树覆盖文件。

  • 将 FILE_SUFFIX 设为 mouse 并为 native_sim 构建时，使用 prj_mouse.conf 和 boards/native_sim.overlay。因为没有 native_sim_mouse.overlay，所以回退到 native_sim.overlay。

  • 将 FILE_SUFFIX 设为 mouse 并为 qemu_cortex_m3 构建时，使用 prj_mouse.conf 和 boards/qemu_cortex_m3_mouse.overlay。

应用专用代码

应用源码通常放在应用的 src 目录。文件较多时可在 src 下按需建立多层子目录。

应用源码不应使用内核保留的符号前缀。详情见命名约定。

第三方库代码

可以在应用的 src 目录之外构建库，但应用与库必须面向相同的应用二进制接口（ABI）。多数架构通过编译器选项控制目标 ABI，因此应用与库的相关选项必须一致。用于衔接二者的代码也可能需要访问 Zephyr 内核头文件。

为便于集成第三方组件，Zephyr 提供了 CMake 函数，使应用构建脚本可以获取 Zephyr 的编译器选项。这些函数在 cmake/modules/extensions.cmake 中定义并附有文档，命名遵循 zephyr_get_<type>_<format>。

通常需要向第三方构建系统导出以下变量。

  • CMAKE_C_COMPILER, CMAKE_AR.

  • ARCH、BOARD 以及若干标识 Zephyr 内核版本的变量。

示例项目 samples/application_development/external_lib 展示了其中部分功能。

构建应用

Zephyr 构建系统将应用的各个组件编译并链接为一个应用镜像（image），可在模拟硬件或真实硬件上运行。

与其他基于 CMake 的系统一样，构建分为两个阶段：先使用 cmake 命令行工具，指定生成器（generator）并生成构建文件。生成器决定第二阶段采用的原生构建工具。随后运行该工具，编译源码并生成镜像。相关概念见 CMake 官方文档的CMake 入门。

Zephyr 的默认构建工具是元工具 west，它会调用 cmake 及底层构建工具（ninja 或 make）；也可以直接运行 cmake。在 Linux 和 macOS 上可选择 make 或 ninja 生成器；Windows 不支持 make，因此需要 ninja。为简洁起见，下文统一使用 ninja。用 west build 构建时，底层默认使用 ninja。

例如，为 reel_board 板构建 Hello World 示例：

使用 west：

# From the root of the zephyr repository
west build -b reel_board samples/hello_world

使用 CMake 和 ninja：

# From the root of the zephyr repository
# Use cmake to configure a Ninja-based buildsystem:
cmake -Bbuild -GNinja -DBOARD=reel_board samples/hello_world

# Now run the build tool on the generated build system:
ninja -Cbuild

在 Linux 和 macOS 上，也可用 make 代替 ninja 构建：

使用 west：

  • 仅本次使用 make：在 west build 命令行后添加 -- -G"Unix Makefiles"。示例见 west build 文档。

  • 今后默认使用 make：运行 west config build.generator "Unix Makefiles"。

直接使用 CMake：

# From the root of the zephyr repository
# Use cmake to configure a Make-based buildsystem:
cmake -Bbuild -DBOARD=reel_board samples/hello_world

# Now run the build tool on the generated build system:
make -Cbuild

基础知识

  1. 进入应用目录 <app>。

  2. 输入以下命令，为命令行指定的开发板构建应用的 zephyr.elf 镜像：

    使用 west：

    west build -b <board>

    使用 CMake 和 ninja：

    mkdir build && cd build

# Use cmake to configure a Ninja-based buildsystem:
cmake -GNinja -DBOARD=<board> ..

# Now run the build tool on the generated build system:
ninja

    也可通过 CONF_FILE 指定另一个 .conf 文件，使用其中的配置构建应用。其设置会覆盖应用 .config 文件或默认 .conf 文件中的设置。例如：

    使用 west：

    west build -b <board> -- -DCONF_FILE=prj.alternate.conf

    使用 CMake 和 ninja：

    mkdir build && cd build
cmake -GNinja -DBOARD=<board> -DCONF_FILE=prj.alternate.conf ..
ninja

    如前所述，可导出环境变量 BOARD 和 CONF_FILE，或在 CMakeLists.txt 中用 set() 语句设置二者，持久指定板卡与配置。west 还支持指定默认开发板。

构建目录的内容

使用 Ninja 生成器时，构建目录的结构如下：

<app>/build
├── build.ninja
├── CMakeCache.txt
├── CMakeFiles
├── cmake_install.cmake
├── rules.ninja
└── zephyr

构建目录中值得关注的文件和子目录包括：

  • build.ninja：供构建工具据此构建应用。

  • zephyr 子目录：生成的构建系统的工作目录，大部分生成文件存放在这里。

运行 ninja 后，以下产物写入构建目录的 zephyr 子目录。（这不是 Zephyr 基目录，不要与上文存放 Zephyr 源码等内容的位置混淆。）

  • .config：构建应用实际使用的配置。

    说明

    配置一旦更新，旧的 .config 就会保存为 .config.old，便于比较前后的差异。

  • 各种目标文件和归档文件（.o 和 .a），包含已编译的内核与应用代码。

  • zephyr.elf：链接在一起的应用和内核二进制文件。也支持 .hex、.bin 等其他输出格式。

重新构建应用

及时测试每次修改通常能加快开发。应用越来越复杂时，经常重新构建可以减少调试困难。大幅改动源码、CMakeLists.txt 或配置后，建议重新构建并测试。

重要

Zephyr 只重新构建可能受改动影响的部分，因此增量构建通常比首次构建快得多。

有时构建系统漏编了必要文件，导致结果不正确。此时可按以下步骤强制从头构建整个应用：

  1. 在主机上打开终端，进入构建目录 <app>/build。

  2. 根据是使用 west 还是直接使用 cmake，运行下面的相应命令，删除应用的生成文件，但保留包含当前配置的 .config。

    west build -t clean

    或者

    ninja clean

    也可运行以下相应命令来删除全部生成文件，包括保存相应板卡当前应用配置的 .config 文件。

    west build -t pristine

    或者

    ninja pristine

    使用 west 时，可让它在必要时自动清空构建目录并从头构建。

  3. 按上文构建应用中的步骤重新构建应用。

为特定开发板修订版构建

同一开发板若有细微的硬件差异，Zephyr 支持为其指定多个硬件修订版。这样只需在板级支持文件中调整差异，无需为每一版复制创建开发板目录列出的所有文件。

为特定修订版构建时，将普通的 <board> 或 <board>/<qualifiers> 换成 <board>@<revision> 或 <board>@<revision>/<qualifiers>。例如：

使用 west：

west build -b nrf9160dk@0.14.0/nrf9160/ns

使用 CMake 和 ninja：

mkdir build && cd build
cmake -GNinja -DBOARD=nrf9160dk@0.14.0/nrf9160/ns ..
ninja

请查阅板卡文档，确认是否存在多个修订版以及支持哪些版本。

指定修订版后，CMake 在配置阶段会显示实际采用的版本，例如：

-- Board: plank, Revision: 1.5.0

运行应用

应用镜像可在真实开发板或仿真硬件上运行。

在开发板上运行

Zephyr 支持的大多数板都可使用 west flash 将编译好的二进制文件烧写到板上并运行。操作步骤如下：

  1. 按构建应用中的说明构建应用。

  2. 确认开发板已连接主机，通常通过 USB 连接。

  3. 在构建目录 <app>/build 中运行以下命令，将编译好的 Zephyr 镜像烧写到板上并运行：

    west flash

构建系统结合板级支持文件，调用对应硬件的工具写入 Zephyr 二进制文件，然后运行它。

每次执行烧写命令时，应用都会重新构建并再次烧写。

若板级支持不完整，Zephyr 构建系统可能不支持烧写。如果提示没有烧写支持，请查阅开发板文档，了解其他烧写方式。

说明

在 Linux 上，普通用户通过 USB 访问开发板时往往需要安装板卡专用的 udev 规则。如果烧写失败，可查阅板卡文档确认。

在仿真器中运行

Zephyr 内置了对 QEMU 的支持。可以在将程序写入实际目标硬件之前，或用仿真代替实机，在虚拟环境中运行并测试应用。

Windows 上的附加步骤见入门之后。

在 QEMU 中运行应用的步骤如下：

  1. 按构建应用所述，为一块 QEMU 虚拟板构建应用。

    例如，可将 BOARD 设为：

    • qemu_x86：仿真 x86 开发板。

    • qemu_cortex_m3：仿真 Arm Cortex-M3 开发板。

  2. 在构建目录 <app>/build 中执行以下任一命令，在 QEMU 中运行 Zephyr 程序：

    west build -t run

    或者

    ninja run

  3. 按 Ctrl+A, 再按 X，停止在 QEMU 中运行的应用。

    应用停止，终端重新显示命令提示符。

每次执行运行命令，都会重新构建并运行应用。

说明

若已安装 Zephyr SDK，run 目标默认使用 SDK 自带的 QEMU。要切换版本，请设置环境变量 QEMU_BIN_PATH 为目标 QEMU 可执行文件的路径。

说明

在目标名后追加 _<emulator> 可选择特定仿真器；例如 QEMU 对应 west build -t run_qemu 或 ninja run_qemu。

自定义开发板、设备树与 SoC 定义

如果 Zephyr 尚不支持所用的板或平台，可在应用中添加板卡、设备树和 SoC 定义，不必修改 Zephyr 源码树。

树外板卡和 SoC 的目录布局与 Zephyr 源码树内类似。沿用这种结构，初期开发结束后更容易将平台相关代码提交上游。

按下列结构，在应用或独立仓库中添加自定义开发板：

boards/
soc/
CMakeLists.txt
prj.conf
README.rst
src/

其中 boards 保存构建目标板的相关文件：

.
├── boards
│   └── vendor
│       └── my_custom_board
│           ├── doc
│           │   └── img
│           └── support
└── src

soc 保存 SoC 代码。自定义板也可使用 Zephyr 源码树中已有的 SoC 支持。

开发板

在 boards 下，用厂商名称作为 my_custom_board 的目录名。提交 Zephyr 上游时必须与 dts/bindings/vendor-prefixes.txt 中的厂商前缀一致；非厂商板则用 others。

本地可省略文档（doc/）和支持文件（support/），但提交 Zephyr 上游时需要提供。

my_custom_board 的内容应遵守 Zephyr 开发板通用规范，并提供以下文件：

board.yml
my_custom_board_defconfig
my_custom_board.dts
my_custom_board.yaml
board.cmake
board.h
CMakeLists.txt
doc/
Kconfig.my_custom_board
Kconfig.defconfig
support/

建立好目录结构后，通过 CMake 参数 -DBOARD_ROOT 指向自定义板文件位置，即可针对该板构建应用：

使用 west：

west build -b <board name> -- -DBOARD_ROOT=<path to boards>

使用 CMake 和 ninja：

cmake -Bbuild -GNinja -DBOARD=<board name> -DBOARD_ROOT=<path to boards> .
ninja -Cbuild

这会使用自定义板配置，并在应用目录中生成 Zephyr 二进制文件。

也可在应用的 CMakeLists.txt 中定义 BOARD_ROOT。务必在通过 find_package(Zephyr ...) 引入 Zephyr 基础构建逻辑之前设置它。

说明

在 CMakeLists.txt 中设置 BOARD_ROOT 时必须使用绝对路径，例如 list(APPEND BOARD_ROOT ${CMAKE_CURRENT_SOURCE_DIR}/<extra-board-root>)。使用 -DBOARD_ROOT=<board-root> 时既可用绝对路径也可用相对路径，后者以应用目录为基准。

说明

使用 sysbuild 时，必须在模块或 sysbuild 的 CMakeLists.txt 中定义 BOARD_ROOT。详见配置 sysbuild 内部状态。

SoC 定义

与板级支持类似，SoC 的目录布局沿用 Zephyr 源码树中的惯例，例如：

soc
└── st
    └── stm32
        ├── common
        └── stm32l0x

soc/Kconfig 会在 Kconfig 中创建顶层 SoC/CPU/Configuration Selection 菜单。

可用 CMake 变量 SOC_ROOT 将树外 SoC 定义加入此菜单。变量值是以分号分隔的目录列表，各目录包含 SoC 支持文件。

对于上述结构，可添加以下文件以在菜单中加载更多 SoC。

soc
└── st
    └── stm32
        └── stm32l0x
            ├── Kconfig
            ├── Kconfig.soc
            └── Kconfig.defconfig

上述 Kconfig 文件可以描述 SoC，也可以继续加载其他 SoC 的 Kconfig 文件。

例如，要在此结构中加载专用于 stm32l0 的 Kconfig 文件，

soc
└── st
    └── stm32
        ├── Kconfig.soc
        └── stm32l0x
            └── Kconfig.soc

可在 st/stm32/Kconfig.soc 中加入以下内容：

rsource "*/Kconfig.soc"

SoC 目录就位后，通过 CMake 参数 -DSOC_ROOT 指向自定义平台文件所在位置，即可面向该平台构建：

使用 west：

west build -b <board name> -- -DSOC_ROOT=<path to soc> -DBOARD_ROOT=<path to boards>

使用 CMake 和 ninja：

cmake -Bbuild -GNinja -DBOARD=<board name> -DSOC_ROOT=<path to soc> -DBOARD_ROOT=<path to boards> .
ninja -Cbuild

这会使用自定义平台配置，在应用目录中生成 Zephyr 二进制文件。

如何在模块的 zephyr/module.yml 中设置 SOC_ROOT，见构建设置。

也可在应用的 CMakeLists.txt 中定义变量 SOC_ROOT。务必在用 find_package(Zephyr ...) 引入 Zephyr 基础构建逻辑之前设置它。

说明

在 CMakeLists.txt 中设置 SOC_ROOT 时必须使用绝对路径，例如 list(APPEND SOC_ROOT ${CMAKE_CURRENT_SOURCE_DIR}/<extra-soc-root>。使用 -DSOC_ROOT=<soc-root> 时既可用绝对路径也可用相对路径，后者以应用目录为基准。

设备树定义

构建系统会在 APPLICATION_SOURCE_DIR、BOARD_DIR 和 ZEPHYR_BASE 中查找设备树目录树。可创建以下目录结构，添加其他设备树根目录（DTS_ROOT）：

include/
dts/common/
dts/arm/
dts/
dts/bindings/

将 arm 替换为实际架构名。各子目录均为可选；绑定目录保存绑定，其余目录可存放设备树源文件引用的文件。

目录就位后，可通过 CMake 缓存变量 DTS_ROOT 指定其位置：

使用 west：

west build -b <board name> -- -DDTS_ROOT=<path to dts root>

使用 CMake 和 ninja：

cmake -Bbuild -GNinja -DBOARD=<board name> -DDTS_ROOT=<path to dts root> .
ninja -Cbuild

也可在应用的 CMakeLists.txt 中设置该变量。务必在用 find_package(Zephyr ...) 引入 Zephyr 基础构建逻辑之前设置它。

说明

在 CMakeLists.txt 中设置 DTS_ROOT 时必须使用绝对路径，例如 list(APPEND DTS_ROOT ${CMAKE_CURRENT_SOURCE_DIR}/<extra-dts-root>。使用 -DDTS_ROOT=<dts-root> 时既可用绝对路径也可用相对路径，后者以应用目录为基准。

设备树源文件先经过 C 预处理器，因此也可包含位于 DTS_ROOT 目录中的文件。按惯例，设备树包含文件的扩展名为 .dtsi。

也可通过 CMake 缓存变量 DTS_EXTRA_CPPFLAGS 指定预处理指令，控制设备树文件的内容：

使用 west：

west build -b <board name> -- -DDTS_EXTRA_CPPFLAGS=-DTEST_ENABLE_FEATURE

使用 CMake 和 ninja：

cmake -Bbuild -GNinja -DBOARD=<board name> -DDTS_EXTRA_CPPFLAGS=-DTEST_ENABLE_FEATURE .
ninja -Cbuild
