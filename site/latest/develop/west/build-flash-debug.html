构建：west build

提示

运行 west build -h 可快速查看用法。

build 可从源码构建 Zephyr 应用。可以通过 west config 配置其行为。

命令默认会根据当前目录判断要执行的操作：

  • 若当前工作目录下存在名为 build 的 Zephyr 构建目录，则执行增量构建。从 Zephyr 构建目录内运行 west build 时也是如此。

  • 否则，如果在 Zephyr 应用源码目录运行 west build，且没有找到构建目录，就会新建一个目录并在其中编译应用。

基础知识

使用 west build 最简单的方法，是进入应用根目录（包含应用 CMakeLists.txt 的目录），然后运行：

west build -b <BOARD>

其中 <BOARD> 是目标开发板名称，与直接调用 CMake 时在 cmake -DBOARD=<BOARD> 中指定的名称相同。

提示

运行 west boards 可列出所有受支持的开发板。

west build 会创建名为 build 的构建目录，在其中运行 CMake 生成构建系统，然后编译应用。若 west build 找到已有的构建目录，则在该目录内执行增量构建，不重新运行 CMake。可用 --cmake 强制重新运行 CMake。

已有构建目录时，无需指定 --board；west build 可从 CMake 缓存读取板名。新建构建时，依次检查 --board 选项、BOARD 环境变量和 build.board 配置项。

系统构建（sysbuild，多域构建）

通过 系统构建（Sysbuild） 可创建多域构建系统，把面向单块或多块开发板的多个镜像组合起来。

使用 west build 时，加上 --sysbuild 即可选择 系统构建（Sysbuild） 基础设施，构建多个域（domain）。

更多用法见 系统构建（Sysbuild） 指南。

提示

启用配置项 build.sysbuild 可让 west build 默认使用 sysbuild；个别构建可用 --no-sysbuild 禁用它。

west build 通过顶层构建目录构建 sysbuild 指定的全部域。

若只想构建多域工程中的一个域，可使用 --domain 参数。

示例

以下按用途给出 west build 的示例。

强制重新运行 CMake

要强制重新运行 CMake，请使用 --cmake（或 -c）：

west build -c

设置默认开发板

要让 west build 默认针对 reel_board 构建：

west config build.board reel_board

（也可使用 Zephyr 支持的其他开发板，并不限于 reel_board。）

指定源码目录和构建目录

要显式指定应用源码目录，请将其路径作为位置参数传入：

west build -b <BOARD> path/to/source/directory

要显式指定构建目录，请用 --build-dir（或 -d）：

west build -b <BOARD> --build-dir path/to/build/directory

要更改默认构建目录 build，可用配置项 build.dir-fmt。它支持以格式字符串命名构建目录，例如：

west config build.dir-fmt "build/{board}/{app}"

按上述配置，运行 west build -b reel_board samples/hello_world 将使用构建目录 build/reel_board/hello_world。该选项详见配置选项。

指定构建目标

用 --target（或 -t）指定要执行的构建目标。

例如，在安装了 QEMU 的主机上，可使用 run 目标，一条命令就能为仿真的 qemu_x86 板构建并运行 Hello World 示例：

west build -b qemu_x86 -t run samples/hello_world

再如，用 -t 列出所有构建目标：

west build -t help

最后，用 -t 运行 pristine 目标会删除构建目录中的所有文件：

west build -t pristine

干净构建（pristine build）

干净的（pristine）构建目录相当于新建目录：以往构建留下的产物都已移除。

要让 west build 在重新运行 CMake 生成构建系统前先清理构建目录，使用 --pristine=always（或 -p=always）。

单独指定 --pristine 或 -p 而不传值，等同于指定 always。例如，以下命令等效：

west build -p -b reel_board samples/hello_world
west build -p=always -b reel_board samples/hello_world

默认情况下，west build 不会检测构建目录是否需要清理。例如，把旧目录用于不同的 --board 时，可能出现错误。

使用 --pristine=auto 后，west build 会检测部分此类情况，并在尝试构建之前清空构建目录。

提示

要始终执行干净构建，运行 west config build.pristine always；要禁用自动判断，运行 west config build.pristine never。详见 west build 配置选项。

显示详细构建输出

要显示 west build 执行的 CMake 和编译器命令，请使用 west 的全局详细输出选项 -v：

west -v build -b reel_board samples/hello_world

仅本次使用的 CMake 参数

要给 west build 调用的 CMake 传递附加参数，在命令行末尾写 --，再写参数。

重要

这样传入 CMake 参数会强制 west build 重新运行 CMake 配置，即使已有构建系统也不例外。增量构建因此会变慢，但仍比从头构建快得多。

首次使用 -- 生成构建目录之后，后续可用 west build -d <build-dir> 执行增量构建。

也可按下一节持久保存 CMake 参数，这样不会拖慢增量构建。

例如，要将 west build 默认使用的 Ninja 生成器换为 Unix Makefiles，运行：

west build -b reel_board -- -G'Unix Makefiles'

要使用 Unix Makefiles 并把 CMAKE_VERBOSE_MAKEFILE 设为 ON：

west build -b reel_board -- -G'Unix Makefiles' -DCMAKE_VERBOSE_MAKEFILE=ON

即使有多个 CMake 参数，也只写一次 --。传给 west build 的参数中，-- 后面的内容全部转交给 CMake。

要将 DTC_OVERLAY_FILE 设为 enable-modem.overlay，并将该文件用作设备树覆盖文件（devicetree overlay）：

west build -b reel_board -- -DDTC_OVERLAY_FILE=enable-modem.overlay

要将 Kconfig 片段 file.conf 合并进本次构建的 .config：

west build -- -DEXTRA_CONF_FILE=file.conf

持久设置 CMake 参数

上一节是为单次 west build 设置参数。要让 west build 在每次生成新构建系统时都使用相同的 CMake 参数，请设置 build.cmake-args。west build 调用 CMake 生成构建系统时，会按 shell 规则拆分该值，并将结果加入 cmake 命令行。

默认情况下，如果构建目录中已有构建系统，west build 会尽可能复用已有构建系统而不重新生成。因此设置 build.cmake-args 后，应删除已有构建目录或执行一次干净构建（pristine build），以确保设置生效。

例如，要始终启用 CMAKE_EXPORT_COMPILE_COMMANDS，可运行：

west config build.cmake-args -- -DCMAKE_EXPORT_COMPILE_COMMANDS=ON

（额外的 -- 用来强制将剩余内容解释为位置参数。否则 west config 会把 -DVAR=VAL 解释为自己的 -D 选项。）

要启用 CMAKE_VERBOSE_MAKEFILE，让 CMake 始终生成带详细输出的构建系统：

west config build.cmake-args -- -DCMAKE_VERBOSE_MAKEFILE=ON

要在 build.cmake-args 中保存多个参数，将其写成一个可拆分为独立参数的字符串。west build 内部使用 Python 函数 shlex.split() 完成拆分。

例如，同时启用 CMAKE_EXPORT_COMPILE_COMMANDS 和 CMAKE_VERBOSE_MAKEFILE：

west config build.cmake-args -- "-DCMAKE_EXPORT_COMPILE_COMMANDS=ON -DCMAKE_VERBOSE_MAKEFILE=ON"

如果希望将参数另存为文件，可组合 CMake 的 -C <initial-cache> 选项和 build.cmake-args。例如，要设置上例中的选项，也可创建 ~/my-cache.cmake，内容如下：

set(CMAKE_EXPORT_COMPILE_COMMANDS ON CACHE BOOL "")
set(CMAKE_VERBOSE_MAKEFILE ON CACHE BOOL "")

然后运行：

west config build.cmake-args "-C ~/my-cache.cmake"

详情见cmake(1) 手册页及set() 命令的文档。

向底层构建工具传递参数

使用 -o 向底层构建工具传递选项。

此方式适用于基于 ninja（默认选择）或 make 的构建系统。

例如，将 -dexplain 传给 ninja：

west build -o=-dexplain

再如，将 --keep-going 传给 make：

west build -o=--keep-going

注意必须使用 -o=--foo 而非 -o --foo，否则 --foo 会被解释为 west build 的选项。

构建并行度

默认情况下，ninja 会使用所有 CPU 核心，而 make 仅使用一个。两种工具都支持通过 -j 显式设置并行度。

例如，使用 4 个核心构建：

west build -o=-j4

关于 -o 的详细说明见上一节。

构建单个域（domain）

如果多域构建包含 Hello World 和 MCUboot，可用 --domain hello_world 只构建其中一个域：

west build --sysbuild --domain hello_world

可将 --domain 与 --target 组合，构建所选域中的特定构建目标。例如：

west build --sysbuild --domain hello_world --target help

使用配置片段（snippet）

参见使用配置片段（snippets）。

配置选项

可用以下选项配置 west build。

选项

说明

build.board

字符串。如果未传入 --board 且环境中没有设置 BOARD，west build 使用此处指定的开发板。

build.board_warn

布尔值，默认为 true。若设为 false，当 west build 无法确定目标板时不发出警告。

build.cmake-args

字符串。若已设置，每次生成新构建系统时，按 shell 规则拆分并传递给 CMake。见持久设置 CMake 参数。

build.dir-fmt

字符串，默认为 build。west 用此格式字符串创建或查找构建目录。可用的占位项如下：

  • west_topdir：west 工作区的绝对路径，与 west_topdir 命令的输出一致。

  • board：开发板名称。

  • source_dir：CMake 源码目录相对于当前工作目录的路径。若工作目录就在源码目录内，该值为空字符串；Windows 上源目录位于另一驱动器时同样为空，因为无法表示相对路径。未指定源码目录时，默认为当前工作目录。例如，从 <west_topdir>/app1 运行 west build ../app 时，source_dir 得到 ../app（相对于当前工作目录）。

  • source_dir_workspace：源码目录在工作区内时相对于 west_topdir 的路径；否则相对于文件系统根目录（Unix 上为 /，Windows 上为 C:/）。例如，从 <west_topdir>/app1 运行 west build ../app，source_dir 得到 app（相对于 west 工作区目录）。

  • app：源码目录的名称。

build.generator

字符串，默认为 Ninja。它指定生成构建系统所用的 CMake 生成器。只为单次构建选择生成器的方法见上例。

build.guess-dir

字符串。使用 build.dir-fmt 且信息不足以解析目录名时，控制 west 是否尝试推断构建目录。可选值如下：

  • never（默认）：不推断，停止操作，要求用户通过 -d 指定目录。

  • runners：执行使用后端的命令时尝试推断。此类命令通常调用外部工具，例如 flash 和 debug。

build.pristine

字符串。控制 west build 在构建前如何清理构建目录，可取以下值：

  • never（默认）：从不自动清空构建目录。

  • auto：如果已有构建系统，但不清空目录就会构建失败（例如目标板或应用已变更），west build 会在构建前自动清空目录。

  • always：如果存在构建系统，构建前始终清空目录。

build.sysbuild

布尔值，默认为 false。设为 true 时使用 sysbuild 构建应用。

烧写：west flash

提示

运行 west flash -h 获取更多帮助。

基础知识

在 Zephyr 构建目录内运行以下命令，可重新构建并将二进制文件烧写到开发板：

west flash

要指定构建目录，使用 --build-dir（或 -d）：

west flash --build-dir path/to/build/directory

若未指定构建目录，west flash 先检查 build，再检查当前工作目录。若设置配置项 build.dir-fmt（见指定源码目录和构建目录），west flash 会改查指定位置，而不查 build。

选择执行后端（runner）

如果开发板支持多个烧写程序，可用 --runner（或 -r）选择。例如，若 west 默认用 nrfjprog，但也支持 J-Link，可这样覆盖默认选择：

west flash --runner jlink

也可在构建时用 CMake 变量 BOARD_FLASH_RUNNER 修改默认烧写后端，用 BOARD_DEBUG_RUNNER 修改默认调试后端。

例如：

# Set the default runner to "jlink", overriding the board's
# usual default.
west build [...] -- -DBOARD_FLASH_RUNNER=jlink

设置 CMake 参数的方法见仅本次使用的 CMake 参数和持久设置 CMake 参数。

关于 west 使用的 runner 库，见下文配置选项。运行 west flash -H 可列出支持烧写的后端；在构建目录中运行或指定 --build-dir 时，还会显示本板可用后端的附加信息。

覆盖配置

class runners.core.RunnerCaps(commands: set[str] = <factory>, dev_id: bool = False, mult_dev_ids: bool = False, flash_addr: bool = False, erase: bool = False, reset: bool = False, reset_types: bool = False, reset_types_supported: list[str] | None = None, extload: bool = False, tool_opt: bool = False, gdb_init: bool = False, file: bool = False, hide_load_files: bool = False, rtt: bool = False, dry_run: bool = False, skip_load: bool = False, baud_rate: bool = False, batch_debug: bool = False)

此类描述执行后端（runner）支持哪些功能。

每项功能由同名属性表示；标志属性取 True 或 False。

可用功能如下：

  • commands：支持的命令集合，默认为 {'flash', 'debug', 'debugserver', 'attach', 'simulate', 'robot', 'rtt'}。

  • dev_id：是否支持通过 -i 或 --dev-id 指定设备。在同一电脑连接多个调试器时，可用此选项指定本次命令使用哪一个。

  • mult_dev_ids：一次操作能否指定多个设备标识符，以便批量烧写。

  • flash_addr：能否烧写到任意地址。默认为 False；若为 True，后端必须遵循 --dt-flash 选项。

  • erase：是否支持 --erase，在烧写前整片擦除目标上所有可寻址的闪存。对于多核 SoC，可能只擦除目标核对应的区域。此选项可清除影响 Zephyr 镜像行为的旧设置或子系统状态。有些 SoC 也需要它来擦除底层工具无法按扇区擦除的类闪存区域，例如 nRF SoC 的 UICR。

  • reset：是否支持 --reset，在烧写完成后复位设备。

  • reset_types：是否支持 --reset-type=x；x 是由此后端定义的复位类型。

  • reset_types_supported：列出 --reset-type 允许的值。若复位类型动态确定或因设备而异，应省略此项，让取值直接传给底层工具。每个后端还必须能够按自身规则处理 无。建议将行为与 无 相同或最接近的值排在首位。

  • extload：是否支持 --extload；使用时指定一次，将其传给所封装的底层工具。

  • tool_opt：是否支持 --tool-opt（-O）；可重复指定，取值会传给底层工具。

  • gdb_init：是否支持 --gdb-init；可重复指定，按给定顺序把命令追加在后端自身传给 GDB 客户端的命令之后。

  • file：是否支持 --file，显式指定烧写文件，覆盖从构建目录找到的默认文件。

  • hide_load_files：是否隐藏 ELF、HEX 和 BIN 文件参数。

  • rtt：是否支持 SEGGER RTT；支持时会增加 --rtt-address 选项。

  • skip_load：是否支持 --load/--no-load，以便在启动调试会话前跳过向目标加载镜像。此选项仅影响 debug 命令。

  • baud_rate：是否支持 --baud-rate 来设置与目标通信的串口波特率。后端若要提供默认值，应在 do_add_parser() 中使用 parser.set_defaults(baud_rate=...)。

class runners.core.ZephyrBinaryRunner(cfg: RunnerConfig)

二进制文件执行后端（如烧写器、调试器）的抽象基类。

说明：此类的 API 自引入以来很少变动，但不属于 Zephyr 的稳定 API，可能不经通知而更改。

除少数例外，Zephyr 支持的开发板必须提供通用的烧写和调试方式。烧写是把 Zephyr 固件持久写入目标设备以供运行；调试则是让主机上的断点调试器和程序加载器连接到目标。

Zephyr 构建系统提供四个顶层命令来支持这些操作：

  • flash：将先前配置的二进制文件写入开发板，启动目标程序，然后返回。

  • debug：通过调试协议连接开发板，烧写闪存，加载当前二进制文件的符号表，进入调试器界面，直至退出。

  • debugserver：通过开发板支持的调试协议连接目标，然后复位并暂停目标。此时用户可以加载二进制文件中的符号表并连接调试服务器。

  • attach：通过调试协议连接开发板，加载当前二进制文件的符号表，进入调试器界面，直至退出。与 debug 不同，此命令不会烧写闪存。

此类为上述命令提供 API，每个子类简称执行后端（runner）。后端有自己的名称（如 pyocd），并声明支持的命令（如 flash）。开发板（如 nrf52dk/nrf52832）向构建系统声明兼容的后端及其配置方式。

构建系统随后将所需信息写入构建目录。可调用此类的 create() 解析命令行参数并创建后端，也可以直接实例化子类。

定义自己的执行后端需要以下步骤：

  1. 定义 ZephyrBinaryRunner 子类并实现其抽象方法。必要时重写 capabilities()。

  2. 确保定义后端类的 Python 模块被导入，例如修改本包的 __init__.py；否则 get_runners() 无法发现该类。

  3. 在开发板的 board.cmake 中向 Zephyr 构建系统声明后端名称。

其他建议：

  • 若需导入标准库以外的模块，应捕获 ImportError，仅在需要该模块时抛出 RuntimeError。这样既不影响其他后端的用户，也能让使用该后端的用户知道缺少哪项依赖。

  • 如需通过 input() 等方式询问用户，请在类方法 create() 中进行，而不要放在 do_run() 中。这样 __init__() 能获得运行 do_run() 所需的全部信息，也可避免在非命令行应用中意外请求输入。

  • 使用 self.logger 通过标准库的 logging API 记录消息。日志记录器名称为 runner.<your-runner-name()>。

为支持构建系统从命令行调用，每个后端通过共用的 add_parser() 及其调用的 do_add_parser() 定义 argparse 接口，再由 create() 根据 RunnerConfig 和解析后的后端专用参数创建实例。

不同后端使用的主机工具和配置值不同，此类提供统一接口。子类应在构造函数中接收运行命令所需的值；实际执行由 run() 负责。

static require(program: str, path: str | None = None) → str

要求程序在启动前安装。

参数:

  • program – 需要的程序名称, 或程序二进制的路径。

  • path – 查找程序二进制的路径。 默认情况下检查系统 PATH。

如果program 是一条已存在的程序二进制的绝对路径, 此调用将成功。 否则, 如果提供的话, 请尝试在系统 PATH 或给定的 PATH 中找到该程序的名称。

若找到程序，返回其路径；否则抛出 MissingProgram。

static resolve_port_by_chip(detect_func, target, logger, priority_vids=None)

探测串行端口,并返回第一个其连接芯片与正常化目标名称匹配的端口.

参数:

  • detect_func：接收串口设备路径的可调用对象。它负责打开和关闭端口，并返回该端口报告的芯片名称，无法识别时返回 None。

  • 目标：用于匹配的标准化芯片名称。

  • logger：记录进度及诊断信息的 Python 日志记录器，参见 ZephyrBinaryRunner 类。

  • priority_vids：可选的 USB 厂商标识符（VID）列表。优先探测对应端口，以免复位无关的串口适配器。

返回匹配的端口设备路径；没有匹配项时返回 None。

run(command: str, **kwargs)

运行命令("flash","debug","debugserver","attach").

这是执行后端的主入口。

run_server_and_client(server, client, **kwargs)

运行一个忽略SIGINT的服务器,和一个处理它的客户端.

此方法以跨平台的方式执行以下操作：

  • 为 server 命令创建忽略 SIGINT 的 Popen 对象；

  • 暂时忽略 SIGINT，在子进程中运行 client；

  • 客户端退出后清理服务器进程。

  • 如有关键字参数，会同时传给服务器和客户端的子进程调用。

例如，可以用它同时启动 GDB 服务器和客户端。

手动操作

如果不想用 west 烧写或调试开发板，可在构建目录查找生成的二进制文件。文件名取决于开发板与构建系统的集成方式，例如 zephyr/zephyr.elf、zephyr/zephyr.hex。可以用其他工具将其烧写到开发板，也可以按需用于调试，例如从中读取符号表。

默认情况下，这些 west 命令会在烧写和调试前重新构建二进制文件。使用 Zephyr 构建系统的常规目标也能完成此操作；west 命令本身就是这样实现的。
