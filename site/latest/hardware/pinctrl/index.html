引脚控制（Pin Control）

非官方简体中文译本 · H02 · 英文基线 4.5.99 · 全站目录（79 篇） · H 批目录 · 本页英文原文

本页概述引脚控制；接口细节见引脚控制 API。

简介

控制引脚复用和方向、上下拉等参数的硬件模块称为引脚控制器（pin controller）。主要使用者是 SoC 内部外设：例如将 I2C0 的 SDA 信号映射到引脚 PX0。它通常还能设置外设正常运行所需的其他参数，例如按工作频率选择转换速率。选项取决于厂商和 SoC，从简单上下拉到去抖、低功耗模式等不一而足。

硬件实现因厂商和 SoC 而异。一种常见方式是集中式控制：包括信号映射在内的所有参数由同一硬件块（通常称为 pinmux）管理。如下图所示，AF 控制位决定将 PX0 映射到 UART0_TX、I2C0_SCK 还是 SPI0_MOSI；同一模块中的 CONFIG 位控制上下拉等参数。很多 NXP 和 STM32 系列 SoC 采用此模型。

也有厂商或 SoC 采用分布式设计，由多个硬件模块分别负责映射和配置。如下图所示，外设寄存器决定引脚映射；Nordic nRF SoC 就属于这种情况。

硬件方式不同，用户的操作却相同：都是应用一个状态。差别在驱动内部。分布式实现通常更费功夫，因为驱动还需要了解不同外设的寄存器。

引脚控制与 GPIO 的区别

引脚控制与 GPIO 驱动某些功能重叠，例如两者往往都能设置上下拉。Zephyr 的引脚控制驱动负责外设信号复用，以及外设正确工作所需的其他引脚参数，主要使用者是 SoC 外设。GPIO 驱动则用于通用引脚控制，即以软件直接读取或设置引脚逻辑电平。

状态模型

驱动工作前须应用适当的引脚配置。有些配置是静态的，初始化时设置一次即可；有些须在运行时随工作条件改变，例如挂起设备时切换到低功耗模式。Zephyr 用状态（states）描述这些需求，该概念借鉴自 Linux 内核。每个驱动拥有一组状态；每个状态都有唯一名称和一套完整的引脚配置（见下图），各状态彼此独立，无须按固定顺序应用。这也使设备驱动与具体引脚配置解耦。

标准状态

状态的名称和数量取决于驱动需求。许多驱动只需在初始化时应用一个状态，另一些则需要多个。为统一常见用法，约定了下列标准名称及用途。

标准状态名称

状态

标识符

用途

default

PINCTRL_STATE_DEFAULT

设备运行时的引脚状态

sleep

PINCTRL_STATE_SLEEP

设备处于低功耗或睡眠模式时的引脚状态

未来可能增加其他标准状态。

自定义状态

需要自定义状态的驱动，应在作用域中定义名为 PINCTRL_STATE_{STATE_NAME} 的标识符，其中 {STATE_NAME} 是大写状态名。例如支持 mystate 时，驱动必须能看到 PINCTRL_STATE_MYSTATE 的定义。

说明

自定义状态标识符的取值应从 PINCTRL_STATE_PRIV_START 开始。

若需要在驱动外访问自定义状态（如用于动态引脚控制），应在公开头文件中定义其标识符。

跳过状态

通常，固件使用设备树中定义的状态。但某些状态仅在特定构建配置下有用。例如 sleep 一般仅在启用 CONFIG_PM 或 CONFIG_PM_DEVICE 时使用。若某个固件变体不启用这些电源管理选项，理论上应从设备树移除 sleep 状态，避免占用 ROM 存储无用配置。

定义引脚配置时，如果存在名为 PINCTRL_SKIP_{STATE_NAME}、展开为 1 的宏，pinctrl 设备树宏便会跳过对应状态。对于 sleep，pinctrl API 已根据设备电源管理是否可用提供相应定义：

#if !defined(CONFIG_PM) && !defined(CONFIG_PM_DEVICE)
/** Out of power management configurations, ignore "sleep" state. */
#define PINCTRL_SKIP_SLEEP 1
#endif

动态引脚控制

动态引脚控制指在运行时更改引脚配置。同一固件用于稍有差异、外设接到不同引脚的多块板时尤其有用。设置 CONFIG_PINCTRL_DYNAMIC 可启用。

说明

动态引脚控制只应用于尚未初始化的设备。设备运行中修改引脚可能产生意外行为；由于 Zephyr 目前不支持设备反初始化，该功能只应在启动早期使用。

启用后，pinctrl_dev_config 存于 RAM 而非 ROM（状态及引脚配置本身不受此影响）。用户可用 pinctrl_update_states() 将 pinctrl_dev_config 中的状态替换成新集合。驱动之后应用状态时，使用的就是更新后的引脚配置。

设备树中的表示方式

设备树以描述硬件为目的，很适合保存引脚控制配置。以下介绍其中如何表示状态及引脚参数。

状态

每个设备通过 pinctrl-N 属性描述一组状态，其中 N 是从零开始的索引。pinctrl-names 按索引为各状态指定唯一名称，例如 pinctrl-names 的第 0 项对应 pinctrl-0。

periph0: periph@0 {
    ...
    /* state 0 ("default") */
    pinctrl-0 = <...>;
    ...
    /* state N ("mystate") */
    pinctrl-N = <...>;
    /* names for state 0 up to state N */
    pinctrl-names = "default", ..., "mystate";
    ...
};

引脚配置

设备树有多种引脚配置表示法，但本质都是信号复用关系和电气参数。例如将 UART_RX 映射到 PX0 并启用上拉。具体形式主要取决于厂商／SoC，请查对应引脚控制驱动的设备树绑定文件。

下例是一种常用且灵活的形式，可以根据共同参数将引脚分组，减少重复；一个状态的所有引脚参数也集中在同一设备树节点中。

/* board.dts */
#include "board-pinctrl.dtsi"

&periph0 {
    pinctrl-0 = <&periph0_default>;
    pinctrl-names = "default";
};

/* vnd-soc-pkgxx.h
 * File with valid mappings for a specific package (may be autogenerated).
 * This file is optional, but recommended.
 */
...
#define PERIPH0_SIGA_PX0 VNDSOC_PIN(X, 0, MUX0)
#define PERIPH0_SIGB_PY7 VNDSOC_PIN(Y, 7, MUX4)
#define PERIPH0_SIGC_PZ1 VNDSOC_PIN(Z, 1, MUX2)
...

/* board-pinctrl.dtsi */
#include <vnd-soc-pkgxx.h>

&pinctrl {
    /* Node with pin configuration for default state */
    periph0_default: periph0_default {
        group1 {
            /* Mappings: PERIPH0_SIGA -> PX0, PERIPH0_SIGC -> PZ1 */
            pinmux = <PERIPH0_SIGA_PX0>, <PERIPH0_SIGC_PZ1>;
            /* Pins PX0 and PZ1 have pull-up enabled */
            bias-pull-up;
        };
        ...
        groupN {
            /* Mappings: PERIPH0_SIGB -> PY7 */
            pinmux = <PERIPH0_SIGB_PY7>;
        };
    };
};

另一种常见方式为每个引脚配置、每种状态各建节点，板级文件可能更短，但通常不能在多个状态间复用同一节点，因而每种映射和状态都要单独建节点。如果不能自动生成，不推荐此方式。

说明

设备树最终会被解析为 C 头文件，应尽量控制其大小。预生成节点应加上 /omit-if-no-ref/ 前缀，使未被引用的节点被丢弃。

/* board.dts */
#include "board-pinctrl.dtsi"

&periph0 {
    pinctrl-0 = <&periph0_siga_px0_default &periph0_sigb_py7_default
                 &periph0_sigc_pz1_default>;
    pinctrl-names = "default";
};

/* vnd-soc-pkgxx.dtsi
 * File with valid nodes for a specific package (may be autogenerated).
 * This file is optional, but recommended.
 */

&pinctrl {
    /* Mapping for PERIPH0_SIGA -> PX0, to be used for default state */
    /omit-if-no-ref/ periph0_siga_px0_default: periph0_siga_px0_default {
        pinmux = <VNDSOC_PIN(X, 0, MUX0)>;
    };

    /* Mapping for PERIPH0_SIGB -> PY7, to be used for default state */
    /omit-if-no-ref/ periph0_sigb_py7_default: periph0_sigb_py7_default {
        pinmux = <VNDSOC_PIN(Y, 7, MUX4)>;
    };

    /* Mapping for PERIPH0_SIGC -> PZ1, to be used for default state */
    /omit-if-no-ref/ periph0_sigc_pz1_default: periph0_sigc_pz1_default {
        pinmux = <VNDSOC_PIN(Z, 1, MUX2)>;
    };
};

/* board-pinctrl.dts */
#include <vnd-soc-pkgxx.dtsi>

/* Enable pull-up for PX0 (default state) */
&periph0_siga_px0_default {
    bias-pull-up;
};

/* Enable pull-up for PZ1 (default state) */
&periph0_sigc_pz1_default {
    bias-pull-up;
};

说明

不建议在预定义节点中加入默认引脚配置。配置往往与板级设计、外设工作条件相关，应由板级代码决定。例如板上可能已有上拉，或者上拉阻值取决于总线速率。默认值的另一问题是用户可能不知道它存在，例如：

/* not evident that "periph0_siga_px0_default" also implies "bias-pull-up" */
/omit-if-no-ref/ periph0_siga_px0_default: periph0_siga_px0_default {
    pinmux = <VNDSOC_PIN(X, 0, MUX0)>;
    bias-pull-up;
};

实现指南

引脚控制驱动

引脚控制驱动只须实现 pinctrl_configure_pins()，它接收待应用的引脚配置数组。若设置 CONFIG_PINCTRL_STORE_REG，还会接收与这些引脚关联的设备寄存器地址，供需要执行设备专用操作的驱动使用。

配置使用厂商／SoC 专有的不透明类型 pinctrl_soc_pin_t，定义在 Zephyr 包含路径内名为 pinctrl_soc.h 的头文件中；它可以是整数，也可以是多字段结构。pinctrl_soc.h 还须定义 Z_PINCTRL_STATE_PINS_INIT 宏，接受节点标识符和属性名（pinctrl-N），据此为该节点 pinctrl-N 属性中的所有引脚配置生成初始化器。

厂商可选择适合自家硬件的设备树表示，但应遵循下列约定：

  • 使用 pinctrl-N（N=0、1……）和 pinctrl-names 定义引脚控制状态。两项属性定义于 dts/bindings/pinctrl/pinctrl-device.yaml。

  • 使用 dts/bindings/pinctrl/pincfg-node.yaml 中的标准引脚配置属性。

如果同一厂商已在其他操作系统（如 Linux）使用不同表示方式，也可能予以接受。

设备驱动

以下说明设备驱动如何用 pinctrl API 配置自身引脚。

须修改与设备 compatible 匹配的绑定文件，使其包含 pinctrl-device.yaml。例如：

include: [base.yaml, pinctrl-device.yaml]

此文件为设备添加 pinctrl-N 和 pinctrl-names 属性。

驱动使用 pinctrl API 需完成两步。先用 PINCTRL_DT_DEFINE 或 PINCTRL_DT_INST_DEFINE 定义包括所有状态、引脚在内的配置，再保存对该设备实例 pinctrl_dev_config 的引用，以供后续调用。可通过 PINCTRL_DT_DEV_CONFIG_GET 或 PINCTRL_DT_INST_DEV_CONFIG_GET 获取该引用。

设备及其引脚控制配置只通过变量命名约定关联。给定设备树节点标识符，就能根据 pinctrl_dev_config 的命名规则找到对应实例。因此只有需要引脚控制的设备才保存配置引用，可减少 ROM 占用。

定义配置并保存引用后，通常用 pinctrl_apply_state() 应用状态。如果已提前缓存状态（如在初始化时），可用底层接口 pinctrl_apply_state_direct() 跳过查找。但查找开销预计很低，一般建议使用 pinctrl_apply_state()。

以下是使用 pinctrl API 的完整设备驱动示例。

/* A driver for the "mydev" compatible device */
#define DT_DRV_COMPAT mydev

...
#include <zephyr/drivers/pinctrl.h>
...

struct mydev_config {
    ...
    /* Reference to mydev pinctrl configuration */
    const struct pinctrl_dev_config *pcfg;
    ...
};

...

static int mydev_init(const struct device *dev)
{
    const struct mydev_config *config = dev->config;
    int ret;
    ...
    /* Select "default" state at initialization time */
    ret = pinctrl_apply_state(config->pcfg, PINCTRL_STATE_DEFAULT);
    if (ret < 0) {
        return ret;
    }
    ...
}

#define MYDEV_DEFINE(i)                                                    \
    /* Define all pinctrl configuration for instance "i" */                \
    PINCTRL_DT_INST_DEFINE(i);                                             \
    ...                                                                    \
    static const struct mydev_config mydev_config_##i = {                  \
        ...                                                                \
        /* Keep a ref. to the pinctrl configuration for instance "i" */    \
        .pcfg = PINCTRL_DT_INST_DEV_CONFIG_GET(i),                         \
        ...                                                                \
    };                                                                     \
    ...                                                                    \
                                                                           \
    DEVICE_DT_INST_DEFINE(i, mydev_init, NULL, &mydev_data##i,             \
                          &mydev_config##i, ...);

DT_INST_FOREACH_STATUS_OKAY(MYDEV_DEFINE)
